## Problem and implementation
The existing Metal backend used `[MTLTexture replaceRegion:...]` for array-slice VT atlas updates. CPU-side texture mutations may conflict with prior in-flight GPU readers when LRU recycles a physical page. The new `Texture2DArray && !t->mips` path copies caller-provided RGBA/upload rows into a 256-byte row-aligned shared MTLBuffer and records `copyFromBuffer:...toTexture:...` on a Metal blit encoder. If a frame command buffer exists it uses that command buffer (only between active encoders); otherwise it creates and commits a standalone command buffer on the same Metal queue. A completion handler retains the staging buffer until GPU completion. Encoder/staging allocation errors are returned as `false`.

This converts reuse into ordered **GPU queue writes** instead of CPU writes directly mutating a potentially sampled texture. Explicit authored physical mip levels are separate blits and remain covered by VirtualTextureStreamer atomic page-table publication after the last upload *submission*. The GPU queue provides execution order with earlier rendering on that queue; `true` is not a completed GPU fence.

## Boundaries
The new branch only handles non-auto-mip Texture2DArray updates (virtual texture atlas and other explicit-mip arrays). Ordinary 2D, cube and 3D resources still use their legacy replaceRegion code. Other command queues, out-of-band external texture access, stale in-flight descriptor lifetime, and device-loss recovery are NOT proven safe by this change.

It also intentionally rejects array uploads while any Metal render, compute or GPU ICB encoder is active. Streaming should drain between passes. Note that Metal's blit buffer-to-texture alignment and resource retention must be validated on actual macOS/iOS targets before enabling broadly. No GPU global wait was introduced.
