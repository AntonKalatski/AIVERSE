# Universal queued ECS impact resolution

Read `AGENTS.md`, `docs/ecs-mechanic-composition.md`,
`docs/ecs-all-features-migration-plan.md`,
`skills/gameplay/aiverse-ecs-ordered-impact/SKILL.md`,
and `docs/editor-unification-handoff.md`.

Use this package when a game needs a **separately scheduled** impact
resolution barrier, rather than direct damage execution inside its motion
system. The pure `resolveOrderedProjectileImpact` policy remains appropriate
for legacy mechanics requiring immediately applied damage between projectiles.

## Public API

Header: `<aiverselib/genre/EcsImpactQueueSystems.h>`
Target: `AIVERSE::lib_ecs_impact_queue` (depends on
`AIVERSE::lib_ecs_ordered_impact`).

In `GameModule::setup`, create `World::setResource<OrderedImpactQueue>()`
and register `addOrderedImpactResolutionSystem(sim, name, directHit,
afterDirect, queryArea, canSplash, splashHit)`.

Submit validated `OrderedProjectileImpact` with
`enqueueOrderedImpact(world, impact)`. The returned nonzero
`uint64_t` is a monotonic sequence number. Queue capacity is bounded.
The system processes requests **in enqueue order** and does not sort by
genre, actor, collider, or network delivery order.

The callbacks supply the game's damage, shields, faction/LOS/filtering,
status effects and spatial query. For each projectile, the dispatcher calls:

1. `directHit(sim, request, target)`
2. `afterDirect(sim, request, target)`
3. If splash radius is positive, `queryArea(..., visit)`, calls
   `canSplash` on nonprimary candidates and `splashHit` for accepted ones.

A request generated by a callback belongs to the **next** registered
barrier invocation. This is deliberate, deterministic, rollback-safe
and avoids reentrant structural changes. Do not use this package to
silently alter same-tick damage ordering.

## ECS ownership and persistence

- The queued request contains generation-safe Entity links and Fixed values.
- The `OrderedImpactQueue` world resource holds authoritative
  `nextSequence` and pending requests. The library supplies
  `saveOrderedImpactQueue` (versioned Archive v1),
  `loadOrderedImpactQueue` (transactional bounds-validated decode) and
  `hashOrderedImpactQueue` (all fields, including Entity generations).
  The hosting `GameModule::serializeState`/`hashState` must call these
  helpers or an equivalent registered serializer; `SimSnapshot` already
  copies the World resource. Do not treat World snapshot support as proof
  that the byte-level save includes the queue.
- HitPoints, armor, inventory, projectile motion and team/faction are
  owned by their respective ECS components or typed host policies.
  The queue **does not** clone or own these game-state fields.
- The host must validate user commands, shooter ownership and allowed
  targets before enqueuing. Inspect `world.alive(entity)` and generation
  before dereferencing optional links; dead targets may be ignored or
  produce miss events according to gameplay rules.
- Schedule structural despawns at a deterministic barrier; avoid
  mutating a component pool while iterating it.

## Verification and migration warnings

Run `ecs_cross_genre_impact_queue_test`: shooter and strategy
hosts check direct/after/area order, faction filtering, no duplicate
splash on the primary target, sequence stability, next-barrier
callback-generated impacts and deep/COW rollback checksums.

**Do not** replace the existing RTS `sysProjectiles` and
`sysProjectilePrograms` with one end-of-tick damage flush.
Their original immediate damage / on-hit / splash / script/shield
side-effect order is part of the deterministic save/replay contract.
Use the existing synchronous pure policy until an integration
fixture proves that a new barrier is byte/behavior compatible.

This package is currently **opt-in**, and built-in FPS/RTS host
integration, native compiler results, v9 save compatibility and network
rollback remain **unverified**. Record evidence in the handoff after
each implementation commit.
