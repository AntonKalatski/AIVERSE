PRISMA — универсальная постобработка AIVERSE#

PRISMA — название системы полноэкранных эффектов и обработки изображения. Не путать с SpectraFX — системой частиц/VFX. Форматы существующих игр не меняются.

Границы ответственности: PRISMA и SpectraFX#

PRISMA владеет постобработкой итогового изображения: HDR/тонмаппинг, Bloom, color grading/LUT, DoF, Motion Blur, FXAA/TAA/upscaling, screen-space GI/AO/SSR, объёмы камеры, screen-space Shader Graph (domain postfx), render-pass dependencies и performance budgets.

SpectraFX владеет мировыми визуальными эффектами до постобработки: эмиттеры/частицы, дым, огонь, взрывы, ribbons, trail-потоки, CPU/GPU particle simulation, авторинг VFX graph и события ECS. SpectraFX генерирует HDR вклад сцены, PRISMA затем может применить Bloom ко всей сцене. Системы не дублируют друг друга, не зависят от жанра и не включаются в deterministic gameplay state.

Канонические исходники теперь engine/render/Prisma.{h,cpp}, PrismaData.{h,cpp}, PrismaShaders.h, PrismaVolumes.h. Editor: apps/editor/core/PrismaOps.{h,cpp} и apps/editor/windows/PrismaWindow.cpp. Legacy PostFx headers forward to PRISMA, legacy .cpp не содержат реализации. Стабильные JSON postfx, MCP postfx_* и editor saved id postfx не переименовывать: это внешние форматы, а не владельцы кода.

Текущее устройство#

  • Основной C++ API: #include "engine/render/Prisma.h"; класс aiverse::render::Prisma.
  • Совместимость: PostFx и PostFxData — исходные alias/forwarding includes; основная компиляция через Prisma.cpp и PrismaData.cpp. Старые postfx_* MCP имена сохранены.
  • Renderer3D запрашивает PostProcess::scenePass и вызывает resolve(); ScreenLighting при HDR/High выполняет экранное освещение и TAA до финального resolve.
  • Параметры: game.json / карта, postfx с объединением по типу эффекта; панель редактора и MCP-операции уже реализованы.
  • GPU/RHI: GLSL/MSL, HDR RGBA16F с ACES и sRGB, fallback RGBA8; текущая цепочка имеет фиксированный порядок. UI отрисовывается после PRISMA.

PrismaRenderGraph — этап 07 (GPU-free planner)#

engine/render/PrismaRenderGraph.h — первая независимая от RHI реализация описания проходов и ресурсов. PrismaRenderGraph::addResource/addPass/compile строят стабильный топологический порядок, проверяют один writer на ресурс, ошибки идентификаторов, feedback read/write в одном pass и циклы зависимостей. PrismaGraphPlan содержит order, resources (first/last use), slots и число байт выделяемых внутренних текстур. Совместимые по формату и размеру временные ресурсы с непересекающимися lifetime используют один slot; history и ресурсы с allowAlias=false не разделяют slot. External input/output/history передаются вызывающим кодом и не аллоцируются planner.

Важно: это пока только граф зависимостей + lifetime planner, не GPU-executor. Реальный Prisma::resolve() пока исполняет текущий фиксированный pipeline. Нельзя заявлять, что RenderGraph уже управляет рендерингом; следующий этап — RHI-resource pool и execution callbacks с реальными pass bindings. Неправильные зависимости намеренно отклоняются, а не исправляются неявным shader blit.

Тестовый код: tests/render/prisma_graph.cpp, CTest prisma_graph, при AIVERSE_BUILD_TESTS=ON включён в стандартную CMake ALL сборку и ./run-tests.sh. Нативный запуск тестов ещё требуется.

Целевые интерфейсы#

  1. GPU-free PrismaProfile, PrismaVolume, PrismaVolumeStack и разрешение параметров по положению камеры.
  2. Декларативный PrismaGraph с типизированными ресурсами (SceneColor, Depth, Velocity, History, LUT, Output), топологическим порядком и lifetime, без привязки к FPS/RTS.
  3. Эффекты DepthOfField, MotionBlur, AutoExposure, GTAO и LensDistortion как отдельные проходы с quality-tier fallback.
  4. MotionVectors / reactive masks и temporal upscaling; отдельная политика инвалидирования истории при camera cut/LOD/resize.
  5. Профилировщик GPU-проходов, проверка ресурсо-опасных зависимостей, редактор узлов и полная автоматизированная проверка RHI.

Camera Post Process Volumes — этап 08#

PrismaVolumeStack теперь используется в игровом клиенте и в редакторских Scene/Game viewport. На этапе старта карты клиент читает game.json["prismaVolumes"] и map["prismaVolumes"] через parsePrismaVolumes; перед Renderer3D::render(...,&prisma) вызывает prisma.applyCameraVolumes(stack,camera.eye()), после resolvePrisma() сбрасывает настройки к базовому профилю. Editor кэширует профиль по JSON-сигнатуре и разрешает его отдельно для каждой камеры; изменение postfx не мутируется.

Пример game.json (тот же верхнеуровневый блок можно указать на карте):

"prismaVolumes": {
  "volumes": [
    {
      "id": "underwater",
      "shape": "box",
      "center": [12, -5, 20],
      "halfExtents": [15, 6, 12],
      "blendDistance": 3,
      "priority": 10,
      "layerMask": 4294967295,
      "weight": 1,
      "profile": {
        "effects": [
          {"type": "colorGrade", "saturation": 0.5, "temperature": -0.3},
          {"type": "vignette", "intensity": 0.4}
        ]
      }
    }
  ]
}

Формы: global, sphere (center, radius) и box (center, axis-aligned halfExtents). weight в [0,1], blendDistance — дистанция затухания за внешней границей; приоритеты обрабатываются по возрастанию и одинаковые приоритеты сохраняют порядок добавления. layerMask фильтрует камеры, enabled отключает объём.

Профиль внутри volume использует тот же existing postfx schema, не новую библиотеку шейдеров. Указание "hdr" или "enabled" явно включает соответствующий override; отсутствие этих ключей сохраняет значение базового профиля. На карте volume с тем же id заменяет игровой; "replace":true в блоке карты удаляет все game volumes, прежде чем применить map list. Неверные записи пропускаются с issues, authored JSON не меняется.

Ограничения: body volume ещё не ориентированный box (rotation нет), нет spatial index/приоритетного GPU culling, маска камеры по умолчанию all bits; обычные GameClient/Editor применяют mask all. Интерполяция изменяет только явно указанные параметры эффекта (этап 09), остальные параметры, minQuality и пути LUT сохраняют базовые значения. Для native C++ профиля без masks сохраняется legacy full-profile поведение. Дискретные настройки меняются при весе >= 0.5, числовые параметры blend в float на presentation side. Не хранить такой float стек в authoritative ECS state. Новые данные prismaVolumes необязательны и не затрагивают старые проекты. Код: PrismaVolumeData.{h,cpp}, PrismaVolumes.h; CPU tests: tests/render/prisma_volume.cpp / CTest prisma_volume (проверка запуском ещё требуется).

Stage 09 — точечное смешивание параметров#

PrismaVolumeEffectMask в PrismaVolumes.h и PrismaVolumeData.cpp::authoredEffects сопоставляют каждому эффекту bitmask явно указанных параметров из JSON, включая компоненты цвета, flags enabled/minQuality и текстовый путь LUT. Когда volume задаёт только colorGrade.exposure, исходные colorGrade.saturation, contrast, lift/gamma/gain и minQuality не перезаписываются. При отсутствии базового эффекта добавляется нейтральный профиль с плавным входом для ColorGrade/Bloom/эффектов с intensity или amount; для дискретных эффектов — порог 0.5. Для прямого native C++ создания volume без effectMasks сохранено старое full-profile поведение. Тесты prisma_volume расширены на сохранение несвязанных параметров, но нативный запуск ещё требуется.

Stage 10 — визуальное редактирование Camera Volumes#

Панель PRISMA — Постобработка (apps/editor/windows/PrismaWindow.cpp) теперь содержит секцию PRISMA Volumes в текущем scope: вся игра (game.json) или открытая карта. Она умеет создавать глобальный/сферический/box volume; центрировать объём на камеру Scene, редактировать id, enabled, размеры, приоритет, weight, blendDistance, layerMask и вложенные эффекты. Для каждого параметра эффекта рядом есть переключатель наследовать/переопределить: снятие override удаляет соответствующий ключ JSON, а не записывает дефолт. Это соответствует PrismaVolumeEffectMask и предотвращает сброс глобального контраста/насыщенности.

Авторинг использует общий GPU-free makePrismaVolumeJson(id, shape, center) из PrismaVolumeData.h — тот же формат, что runtime-парсер и CPU-тест prisma_volume. Изменения карты идут через MapDoc::beginEdit/touched (undo), изменения игры через сохранение manifest, как в уже существующих PostFX-слайдерах. Scene-камера показывает количество применимых эффектов/объёмов и предупреждения парсера.

Ограничения: нет gizmo-контуров объёма в viewport и нет редактора Shader Graph payload внутри volume — для него остаётся отдельный Shader Graph Editor. UI использует существующий ImGui и editor layout. Ни компиляция, ни GUI smoke/undo parity, ни GPU screenshots на этом этапе не проверены; агент должен подтвердить их нативно перед объединением. Старое ID панели postfx и MCP-команды postfx_* сохранены.

Stage 11 — GPU-free typed RenderGraph dispatch#

engine/render/PrismaGraphDispatch.h adds a header-only, genre-independent dispatchPrismaGraph<Handle>(graph, plan, bindings, callback) contract. PrismaGraphBindings<Handle> contains one entry per graph resource for external handles and one entry per compiled transient slot for physical allocations. PrismaGraphDispatchView::resource(id) resolves a logical resource through the compiled aliasing plan; the host supplies the typed RHI handles, command encoders and texture transitions.

Validation completes before any callback: invalid plans, mismatched binding counts, unbound handles, duplicate pass IDs and invalid resource references are rejected without partially drawing a frame. The callback runs in deterministic topological order, and returning false aborts subsequent passes with an error and exact number of completed passes.

This is not an RHI executor and does not allocate GPU textures, create encoder barriers, perform render passes or bind PRISMA's current fixed chain. An external integration must first create and retain physical slots, manage external/history resource lifetimes, provide synchronization and connect the existing Prisma::resolve calls. Keep the legacy renderer enabled by default until native Metal/GL validation and image parity tests pass.

Tests are appended to tests/render/prisma_graph.cpp / CTest prisma_graph. Native build, CTest and GPU tests have NOT RUN in the GitHub-only agent environment; see docs/handoffs/prisma-stage-11.md.

Stage 12 — Physical Resource Pool (GPU-agnostic)#

engine/render/PrismaGraphResourcePool.h provides a host-owned pool of physical render target handles for PrismaGraphPlan::slots. The host creates targets with a create(format,width,height) callback and releases them with release(handle); this header never calls GPU/RHI APIs.

  • prepare(graph, plan, create, release) reuses allocations with identical format/dimensions and matching history resource name, or creates new targets. It never selects the same allocation twice within a single frame. On allocation failure it releases targets allocated during that prepare call and preserves the previous pool entries.
  • markHistoryWritten(name) marks successfully produced temporal pixels valid; invalidateHistory() discards temporal contents on camera cuts/teleports without discarding reusable GPU storage. If prepare returns a false history-valid bit, the caller must avoid reading the old history and use a non-temporal fallback. Resize changes resource descriptors and always allocates a fresh history.
  • pruneUnused(release) frees allocations not selected by the last successful prepare; clear(release) releases all allocations. Call both only after GPU fence completion, not while earlier frames might still reference them.
  • Use one pool instance per independent camera/view/temporal stream, not one global mutable history across cameras. The pool does not allocate external resource bindings, compute barriers, issue render passes or integrate itself into the existing Prisma::resolve. It is an opt-in host contract.

Tests for reusable physical slots, valid/invalid history, resize/pruning, allocation rollback and clearing are in tests/render/prisma_graph.cpp. Native build/CTest/GPU screenshot verification is NOT RUN for Stage 12. See docs/handoffs/prisma-stage-12.md.

Stage 13 — Opt-in RHI graph adapter (not yet wired into Prisma::resolve)#

engine/render/PrismaRhiExecutor.h bridges the GPU-free Stage 11 graph and Stage 12 allocation pool to the existing gfx::Device API. It creates TextureDesc{renderTarget=true} targets, maps RGBA8/RGBA16F/Depth32F to the backend's supported formats, uses copyColor for one-input/one-output matching RGBA8 Copy passes, and executes Raster callbacks inside balanced beginPass/endPass scopes. Compute callbacks run outside render passes only if Device::supportsCompute() reports support.

A native host explicitly creates a per-camera PrismaRhiExecutor(device) and calls execute(graph,plan,external,raster,compute,optionalDepth) outside any existing pass. Raster callback signature is bool(gfx::Device&, PrismaGraphId, const PrismaGraphDispatchView<gfx::TextureHandle>&); it binds its own pipeline, uniforms and input textures. Compute has the same callback signature but is responsible for opening/closing any compute encoder it needs. optionalDepth must match raster target dimensions if the chosen Metal backend needs a depth attachment. The adapter never calls endFrame, presents, performs implicit shader conversions, or modifies ECS.

Compatibility constraints: currently no RG16F/R32F target formats in gfx::PixelFormat; these graphs fail preflight. The portable copyColor interface only guarantees same-size RGBA8; HDR/other copy operations need explicit raster shader passes. gfx::Device does not expose a universal resource-barrier API. GPU target release and pool reset must happen at a caller-managed safe point after in-flight work finishes. Temporal history is valid only after the host has successfully produced its pixels and explicitly marked it written.

Not a complete render pipeline migration. Prisma::resolve() still uses the legacy, shipped fixed pass chain by default, with no automatic RHI graph execution. The header is an opt-in integration point, and the test addition currently covers only RHI format mappings in tests/render/prisma_graph.cpp. Native build, driver smoke, screenshots and numerical parity remain NOT RUN. See docs/handoffs/prisma-stage-13.md.

Stage 14 — experimental graph-driven SDR FXAA#

The first production call site of PrismaRhiExecutor is an opt-in SDR FXAA prepass in Prisma::resolve(). Set AIVERSE_PRISMA_GRAPH_FXAA=1 to create a two-external-resource graph (scene-fxaa -> fxaa-output) and execute the existing FXAA pipeline, same uniforms and texture bindings, through a single RHI raster pass.

The default code path is unchanged. The experimental path is only used when FXAA is active, the scene is RGBA8/SDR, the FXAA pipeline is valid, both color textures exist, and the matching depth attachment was created. If the graph cannot be compiled/dispatched, the original direct draw() path runs instead. Graph preflight happens before any draw submission; the shader uses exactly one full-screen draw and writes the complete destination. The opt-in pass clears neither color nor depth.

The graph has no internally allocated targets; it uses the existing Sized per-view resources. It does not switch on graph-rendered HDR, bloom, temporal AA, or the final composite. There is no new JSON schema, editor toggle or change to SpectraFX. This is a guarded runtime foothold, not a whole-chain render-graph migration.

GPU parity and native CMake/CTest remain NOT RUN. The test source in tests/render/prisma_graph.cpp checks only graph structure and single-pass binding/dispatch logic, not Metal/GL pixel correctness. For reproduction and outstanding validation, read docs/handoffs/prisma-stage-14.md.

Stage 15 — Bloom Prefilter opt-in and legacy clear parity#

PrismaRhiExecutor::execute now defaults raster passes to the same opaque-black color clear and depth clear as Prisma::draw. An additional clearRasterTargets=false argument is available for explicitly overwrite-only pipelines, but the FXAA and Bloom experimental call sites use the default legacy-compatible behavior. This fixes a known Stage 14 parity risk.

AIVERSE_PRISMA_GRAPH_BLOOM_PREFILTER=1 opts only the first Bloom Prefilter raster pass into PrismaRhiExecutor. It uses the existing kPrefilter shader pipeline, uniform block and one source texture; the input/output resources are externally managed Sized targets (full-resolution input, lower-resolution output), and the graph does not allocate transient textures. In HDR mode both resources are declared RGBA16F, otherwise RGBA8. Both are supported by the existing conditional RHI path.

The rest of the Bloom downsample/upsample chain remains the original direct renderer; the FXAA experiment still uses its independent AIVERSE_PRISMA_GRAPH_FXAA=1 flag. The default path is unchanged and any preflight/allocation failure falls back to Prisma::draw. The experimental raster callback returns true after a submitted draw; failure after GPU submission cannot be rolled back. No full-frame parity has been established.

tests/render/prisma_graph.cpp now has CPU-only graph contracts for SDR and HDR prefilter sizes, bindings, single-dispatch and missing output preflight. These sources have not been compiled or run in this agent environment; Metal/GL screenshots and GPU timings are also NOT RUN. See docs/handoffs/prisma-stage-15.md.

Stage 16 — opt-in full Bloom down/up RenderGraph#

AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 enables an experimental full Bloom Prefilter → Downsample → Upsample graph inside Prisma::resolve(). The flag is off by default. The graph declares one external Scene input and external per-level down/up targets backed by the existing Prisma::Sized per-view texture cache. Every downsample reads the previous mip; each upsample reads the lower intermediate plus the matching down mip. All passes use the existing kPrefilter, kDown and kUp GPU shader programs, exactly the original size-dependent uniforms, tint/radius normalization, source bindings and texture formats (SDR RGBA8; HDR RGBA16F). The host creates the depth attachments for each output size before execution.

The RHI executor now accepts an optional trailing std::function<gfx::TextureHandle(PrismaGraphId)> rasterDepthForPass. When supplied, that attachment replaces the shared rasterDepth for each pass; this is necessary on Metal for different Bloom mip dimensions. Existing Stage 14/15 executor users continue to use the previous optional shared depth and legacy-compatible clear defaults.

Scope/limitations: this is real RHI graph scheduling of Bloom raster passes, but it is not yet adoption of Stage 12's transient graph pool: the host supplies externally cached target textures, which already persist per viewport. There is no automatic RHI in-flight retirement queue or resource barrier API. The complete graph is rebuilt on each opt-in frame, and Prisma::resolve() retains the old path as fallback when graph preflight fails. On any unexpected failure after GPU pass submission, the graph is not replayed (partial rendering must not be double-submitted). No effect outside Bloom was migrated during this stage. If both AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN and the Stage 15 prefilter-only flag are set, the full-chain flag takes precedence on success.

New GPU-free graph tests check 1/2/4 downsample levels for SDR/HDR, topological order, valid binding resolution, and rejection of missing mip targets before pass execution. Those sources have NOT RUN in a native compiler or on a GPU; see docs/handoffs/prisma-stage-16.md.

Stage 17 — per-view compiled Bloom topology cache#

engine/render/PrismaBloomGraph.h provides a GPU-free PrismaBloomGraphCache. configure(sourceWidth,sourceHeight,format,mips) compiles the complete Bloom topology once per source size, HDR/SDR format and mip shape list. Repeated frames with the same structure reuse graph(), plan() and operations(); changed quality/mip sizes trigger compilation of a replacement graph. Failed reconfiguration leaves the previous valid configuration intact, but the renderer never executes that stale graph for the incompatible current layout.

The main Prisma::Sized viewport cache now owns a PrismaBloomGraphCache, so Scene/Game views have separate graph layouts and no cross-view history. The Stage 16 opt-in path AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 uses the cached immutable graph and rebuilds only the frame bindings: threshold/knee/scatter, shader uniforms, source and output texture handles, and per-mip depth attachments. The existing fallback and default-off behavior are preserved. Stage 12 transient target pooling remains a separate future integration; cached topology itself allocates no GPU textures.

This is implementation-only work; CMake, CTest and real GPU validation were intentionally deferred at the user's request. See docs/handoffs/prisma-stage-17.md.

Stage 18 — GPU completion-gated retirement and persistent view executor#

engine/render/PrismaGpuRetirement.h introduces PrismaGpuRetirementQueue<Handle>: retire(handle,submissionFence) transfers an allocation to a pending queue; collect(completedGpuFence, release) invokes the release callback only when the GPU has reported completion through a caller-managed fence/event. drainAfterGpuIdle is valid only after an explicit GPU idle synchronization. A CPU frame counter or gfx::Device::frameSerial() is not a completion fence.

PrismaGraphResourcePool::retireUnused/retireAll now transfer allocations to the caller instead of destroying them immediately. PrismaRhiExecutor::retireUnused/retireAll/collectCompleted wires those operations to its queue and calls RHI destroyTexture after the supplied completed fence. resetAfterGpuIdle() also releases all pending and current allocations, but only if the host has ensured the GPU is idle.

Every Prisma::Sized viewport now holds a lazy persistent std::unique_ptr<PrismaRhiExecutor>, shared by its opt-in FXAA, Bloom prefilter and full Bloom graph calls. It retains resource pool state across frames rather than creating a new executor on every pass. Lifetime is tied to the existing Sized cache. This does not yet make PRISMA use graph-owned Bloom targets; those remain external RHI textures in Sized, and graph execution stays opt-in.

Backend integration constraint: Gfx does not yet provide a portable completed-GPU-fence API. Hosts must pass actual completion signals to collectCompleted. Existing viewport eviction and renderer shutdown still destroy their legacy textures at the current existing release points; they are not automatically made GPU-fence-safe by this opt-in queue. Actual backend fence wiring and transient Bloom pool migration remain future features. Testing/build/GPU verification deliberately deferred at user request. See docs/handoffs/prisma-stage-18.md.

Stage 19 — opt-in graph-owned Bloom mip allocation#

With both AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 and AIVERSE_PRISMA_GRAPH_BLOOM_POOL=1, the complete Bloom RenderGraph can now allocate its own downsample/upsample targets through PrismaGraphResourcePool in the persistent per-viewport RHI executor. Only the input Scene/FXAA color is external. The graph declares every Bloom mip as an internal resource, enabling the planner to alias identical-format/size GPU textures when their lifetimes do not overlap. Without the new pool flag, the existing Stage 16 graph still uses Sized::targets as external resources. Both experimental flags are off by default.

PrismaRhiExecution::resources now maps each logical graph resource to its actual external or pooled RHI texture handle. The final Bloom composite samples resources[cache.outputId()] when pooled mode succeeds. Per-pass depth attachments still come from the established Sized::depths cache; thresholds, scatter, shader pipelines and source UV conventions are unchanged. On graph preflight/allocation failure before GPU submission, the code allocates legacy mip targets and uses the existing Bloom fallback. A failure after GPU submission does not attempt to replay partial passes.

Ownership: pooled RHI textures persist with their viewport executor, rather than being released after each frame. Reconfiguration keeps unselected allocations until explicit safe retirement; their eventual release depends on GPU-completion reporting or a confirmed GPU-idle shutdown. No portable completed-fence backend is yet wired, so automatic mid-flight eviction is deliberately not used. Existing view eviction still follows legacy release assumptions, and memory benefits are not quantified. This experimental path needs build/GPU verification before being enabled by default.

Implementation-only stage: testing intentionally postponed at user request. See docs/handoffs/prisma-stage-19.md.

Stage 20 — Tilt Shift graph opt-in#

AIVERSE_PRISMA_GRAPH_TILT_SHIFT=1 routes the existing three-pass Tilt Shift (downsample, horizontal Gaussian blur, vertical Gaussian blur) through PrismaRhiExecutor. Four logical SSA resources describe the source, first A target, B target and final A target. The two versions of A are deliberately mapped to the same existing physical texture: they are never simultaneously needed, and the intermediate B is separate. Per-pass uniforms and original pipelines are preserved. The default path remains the legacy three draws. Missing resources or failures before GPU submission fall back to it; partially dispatched passes are not replayed. This stage does not yet migrate physical Tilt targets to the graph-owned pool, nor does it activate Tilt Shift by default. Native/GPU tests deliberately NOT RUN per user request. Handoff: docs/handoffs/prisma-stage-20.md.

Stage 21 — Sun Shafts graph opt-in#

Stage 22 — experimental depth-based Depth of Field#

The new depthOfField entry in postfx.effects is handled by the shared PRISMA data catalog (MCP and editor parameter discovery are data-driven). Parameters are focusDepth (0..1 GPU device depth, not metres), focusRange (depth interval), maxBlur (0..16 output pixels) and intensity (0..1). Defaults: 0.5, 0.08, 8, 1 respectively. This entry defaults to High post quality and is classified Heavy in the cost estimation model.

The opt-in AIVERSE_PRISMA_DOF=1 activates one full-resolution nine-neighbour blur pass before SDR FXAA and Bloom; it reads the scene color and render-target depth using the existing GLSL/MSL fullscreen-program path and produces a new color texture used as the source by subsequent effects. The hardware depth is deliberately not represented as physical focus distance, since the PostFrame currently lacks a portable inverse-projection/near-far contract. The blur radius follows the distance between sampled hardware depth and focusDepth, with a central sharp interval. The shader is a bounded, approximate defocus, not cinematic hexagonal bokeh, depth-layer separation or physically accurate lens simulation.

The pass samples the original scene depth, but uses its own scratch depth attachment of matching dimensions, avoiding read/write feedback on the same depth texture. It can run only when the configured effect, opt-in flag, necessary GPU resources and pipeline are present. Without the flag, existing image processing continues unchanged. DoF is disabled on low/medium quality by its default minQuality=high, unless a project explicitly overrides it.

Example game.json postfx.effects entry:

{"type":"depthOfField","focusDepth":0.65,"focusRange":0.08,"maxBlur":6,"intensity":0.8}

Stage 23 — HDR Auto Exposure (GPU log luminance + eye adaptation)#

postfx.effects can now contain {"type":"autoExposure"}. The optional feature remains disabled in rendering unless AIVERSE_PRISMA_AUTO_EXPOSURE=1 is set and the current scene is using linear HDR RGBA16F. On SDR/RGBA8, the effect has no GPU action, because clipped highlights cannot be recovered by metering.

The GPU pipeline in Prisma::resolve() is:

  1. Read scene-linear RGB and store log2 luminance in a half-resolution RGBA16F target (four color taps with Rec.709 luminance coefficients).
  2. Repeatedly average log luminance through a 2x2 pyramid to 1x1. This estimates geometric mean brightness, not a full per-bin histogram.
  3. Determine target exposure 2^(clamp(log2(keyValue)-meanLogL+ compensation, minEV, maxEV)). In a dedicated RGBA16F 1x1 ping-pong pass, blend from previous exposure using 1-exp(-speed*deltaSeconds). speedUp controls increasing exposure (dark->bright output); speedDown decreasing exposure. The time delta is clamped at 0.1s to avoid large jumps after stalls.
  4. Sample the resulting exposure multiplier as TEX8 in the final composite before HDR tonemapping and sRGB conversion. UI remains unprocessed. ColorGrade's manual exposure/compensation still multiplies the automatic result.

Parameters (regular PrismaData catalog and editor/MCP discovery):

parameterdefaultrangemeaning
keyValue0.180.01–1target scene middle grey
minEV-6-12–0lower automatic EV limit
maxEV60–12upper automatic EV limit
speedUp30.01–20brighten response rate, 1/s
speedDown10.01–20darken response rate, 1/s
compensation0-5–5EV bias

Example:

{"type":"autoExposure","keyValue":0.18,"minEV":-4,
 "maxEV":4,"speedUp":2.5,"speedDown":1.0,"compensation":0.0}

Per-Prisma::Sized temporal history uses two 1x1 HDR textures and a previous timestamp. Explicit native Prisma::resetAutoExposure() invalidates history for camera cuts. Project reconfiguration, postprocess toggle and quality changes reset it; a disabled HDR/auto mode also clears valid history. The first enabled frame snaps to the current measured exposure, avoiding reading an uninitialized history texture. No CPU brightness readback is used.

Limitations: the algorithm computes mean log luminance, not a percentile histogram; bright outliers may still influence adaptation, and the measurement is not a physically calibrated light meter. The existing Sized cache is keyed by dimensions rather than stable camera identity, so two viewport cameras of identical size can share their temporal history. A follow-up should add explicit stable view IDs. The fixed exposure sampler uses slot 8, which is also available for the fourth custom ShaderGraph texture (slots 5..8); automatic exposure is skipped for those graphs rather than clobbering user textures. HDR support and blending of 1x1 RGBA16F must be verified on real Metal/GL.

This is an opt-in source implementation with NO native/GPU tests run, per the user's features-first request. Do not enable it globally until verified. Handoff: docs/handoffs/prisma-stage-23.md.

Stage 24 — independent camera history and weighted GPU metering#

The presentation-only API Prisma::setViewId(uint64_t id) selects a stable camera/view identifier before rendering. viewId() const returns it. A view's two 1x1 RGBA16F exposure-history render targets, adaptation timestamp, valid bit and ping-pong index now live in Prisma::exposureViews_, keyed by that ID instead of render dimensions. resetAutoExposure(id) invalidates one view; the no-argument overload invalidates every view. The older target caches remain keyed by size for sharing ordinary temporary textures; exposure history no longer cross-contaminates identically sized Scene and Game cameras.

The editor sets view IDs 1 for Scene and 2 for Game before applyCameraVolumes; GameClient uses ID 3 within its own PRISMA instance. A native project that renders multiple cameras must assign distinct IDs itself. The default ID remains 0 for legacy native projects. Exposure histories are retained until Prisma::shutdown (no automatic per-camera removal/fence retirement yet). IDs must be stable, not increment every frame.

autoExposure has four additional configurable parameters:

  • centerWeight (default 0, range 0..1): 0 = uniform metering, 1 = strongly center-weighted.
  • centerRadius (default 0.35, range 0.05..1): normalized radius for Gaussian center weighting.
  • minMeterLogL (default -10, range -16..0) and maxMeterLogL (default 10, range 0..16): clamp individual pixel log2 luminance in the initial HDR metering pass, reducing extreme brightness influence. This is not percentile-based histogram clipping.

The first pyramid pass now outputs two channels: weighted sum of log2 luminance (R) and sum of weights (G); each later 2x2 pass reduces both components identically. The 1x1 adaptation shader divides R/G before computing target EV. No CPU readback, additional fullscreen texture or extra raster pass is required compared with Stage 23. The format stays RGBA16F throughout.

Example postfx.effects entry:

{"type":"autoExposure","keyValue":0.18,
 "centerWeight":0.75,"centerRadius":0.35,
 "minMeterLogL":-8,"maxMeterLogL":6}

Stage 25 — HDR camera motion vectors and Motion Blur (experimental)#

postfx.effects now accepts motionBlur through the shared, genre-independent PRISMA catalog. The new effect defaults to minQuality: "high" and is opt-in at runtime via AIVERSE_PRISMA_MOTION_BLUR=1; it additionally requires an HDR RGBA16F scene (signed RG motion vectors are not representable in the existing RGBA8 path without encoding).

Parameters: intensity (0..1, default 0.65), maxPixels (0..64, default 20), samples (2..16, default 8), shutterScale (0..2, default 1). Example:

{"type":"motionBlur","intensity":0.6,"maxPixels":20,
 "samples":8,"shutterScale":1.0}

The motion-vector pass samples the current hardware scene depth and reconstructs the world position from the inverse current viewProjection. It projects that position with the previous viewProjection, writing a signed UV velocity currentScreenUV - previousScreenUV into an RGBA16F texture. The next raster pass gathers current-frame scene color along this velocity and blends it with the sharp color. Motion blur is executed before depth of field, FXAA, Bloom and final composite; HUD/UI remains unprocessed. Separate scratch depth attachments avoid sampling and writing the scene depth simultaneously.

The previous camera matrix, validity flag and render dimensions are stored in Prisma::motionViews_ per stable setViewId(), using the same camera identity contract as Auto Exposure. The first rendered frame, resize, changed quality, postprocess toggle or explicit resetMotionHistory(viewId)/no-argument reset invalidates motion history and results in an unblurred frame; it then seeds the matrix for the next frame. setSettings also resets history.

Optional object velocity bridge: a native renderer may call prisma.setObjectMotionVectors(viewId, velocityTexture) each frame with a borrowed, full-resolution texture whose R/G values are signed current-minus-previous normalized screen UV and B is a valid-object pixel mask (B > 0.5). If present, that velocity overrides camera-only velocity for tagged pixels. The borrowed handle is cleared after each resolve. PRISMA does not yet generate per-object velocity buffers from mesh transforms/skinning; the adapter is an integration contract, not automatic object-motion rendering. These inputs are presentation state, not deterministic ECS.

Limitations: this is a camera-reprojection motion blur, not TAA or temporal image accumulation; it does not store previous color, and therefore does not synthesize missing disoccluded samples. Camera cuts must be signaled explicitly to avoid blur across teleports; material transparency and sky (depth≈1) receive zero camera velocity in the basic shader. Neither Metal/GL depth sampling, signed velocity rendering, nor image correctness have been tested. All compilation, CTest and GPU checks remain NOT RUN, per user request. See docs/handoffs/prisma-stage-25.md.

Stage 26 — automatic rigid-object motion vectors (experimental)#

When HDR motionBlur is active with AIVERSE_PRISMA_MOTION_BLUR=1, Renderer3D now has an optional GPU overlay pass for opaque rigid ModelDraw primitives with a stable persistentId. It runs between the scene pass and Prisma::resolve(), outside any open render pass, then sends the RGBA16F velocity texture to PRISMA through the new generic PostProcess bridge. It does not modify gameplay/ECS, and the existing camera-derived vectors remain the fallback for pixels without valid object velocity.

The renderer tracks the previous world transform of each (ModelDraw::persistentId, nodeIndex) in a per-view map. On the first frame or after a camera cut, it records current transforms without drawing a velocity overlay. Once the camera history is valid, it renders each eligible rigid primitive with a dedicated GLSL/MSL shader and ModelVertex position stream. Current and previous model-view-projection matrices produce signed current-minus-previous screen UV motion in RG. B=1 marks visible rigid pixels. A separate scratch depth texture is attached; the shader samples original scene depth and rejects fragments behind the visible surface, so world occlusion/terrain can hide moving objects without writing scene depth.

This pass operates on the existing ModelItems after ordinary batching: individual model node transforms are preserved even if the regular opaque pass used instancing/MDI. The velocity overlay currently uses one regular indexed draw per primitive (not an indirect/instanced velocity submission); it reuses the existing model vertex/index GPU buffers. The overlay render target and depth attachment are owned per PostProcess view ID by Renderer3D and released on its shutdown. No resource is shared between cameras with different stable IDs.

Only rigid, visible, opaque, non-deformed, stable-ID model primitives are eligible. Missing IDs, transparent/masked materials, skinned or baked animated meshes, morph targets, custom geometry and transient immediate draws are skipped. Their pixels continue using the camera-only motion reconstruction. The scene depth test is an approximate epsilon comparison, not a full material/alpha/deformation replay; fast disocclusions and edge artifacts remain possible.

Existing Prisma::setObjectMotionVectors(viewId,texture) stays available for custom native renderers; automatic Renderer3D generation uses the same borrowed-handle bridge via virtual PostProcess::acceptObjectMotionVectors. There is no ECS scheduling or genre-specific integration. Default behavior is unchanged when MotionBlur is not active.

Stage 27 — deformation-aware and instanced object motion vectors#

The optional HDR motionBlur path now contains two new Renderer3D velocity render variants, both active only with AIVERSE_PRISMA_MOTION_BLUR=1:

Rigid velocity instancing. Geometry-equivalent visible opaque rigid ModelItem instances are grouped by source model pointer, first index and index count. A separate 16-instance GLSL/MSL pipeline consumes per-instance current and previous MVP matrices, submitting one drawIndexed(..., instanceCount) per compatible group (up to 16 instances per group). The uniforms occupy at most 2064 bytes; a single item or missing batched pipeline still uses the Stage 26 singleton shader. Matching shader/geometry groups are presentation-only; the existing color draw batching is not altered.

Skinned and morph velocity. Palette-skinned objects and morph-target primitives with a nonzero stable persistentId can produce actual deformed vertex velocities. The renderer snapshots the current joint palette and eight morph weights per (persistentId, nodeIndex, geometryPrimitive), retaining the previous frame's values independently for each camera. A separate shader deforms each mesh vertex for both the current and previous pose, computes two clip positions and stores screen UV displacement. Current and previous U3/U4 blocks hold up to 80 joints (3 rows each); U5 contains the two 8-weight morph arrays and morph atlas parameters; tex8 reuses the existing morph delta texture. GPU skinning/morph math is kept separate from the deterministic simulation and is not a CPU-skinned mesh upload. A missing previous pose or changed source model identity causes the deformable primitive to skip object-velocity override rather than invent movement.

Depth-edge motion blur. Motion Blur now samples the original scene depth at each color gather position and reduces contributions across large depth discontinuities. This protects foreground outlines against unrelated background colors, although the rejection threshold is based on non-linear hardware depth, so it is a conservative approximation, not physically exact depth-layer motion reconstruction. Prisma::buildProgram supports depth2d<float> for explicitly marked depth samplers on Metal while keeping GLSL sampler2D conventions.

Eligibility remains intentionally conservative: visible, opaque non-displaced primitives with stable IDs. Baked animation (whose pose comes from clip textures), material ShaderGraph vertex displacement, transparent/masked models and custom geometry are not yet handled by the new deformed-velocity pipeline. Velocity target resize, first frame and camera cuts seed history rather than extrapolating invalid motion. Renderer3D owns lazy velocity shader/pipeline and target lifetime.

Stage 28 — baked clip motion, alpha-cutout velocity and depth thresholds#

The experimental motionBlur pipeline now includes a baked-clips vertex velocity shader variant. For a ModelItem with baked=true, the renderer records the current anim values (clip A row, clip B row, blend) and world matrix by stable (persistentId, nodeIndex, geometryPrimitive). The new GLSL/MSL vertex shader reads the original baked bone atlas (tex7) and original per-primitive joint palette. Current and previous clip rows and interpolation are sampled separately to reconstruct both deformed vertex positions. The velocity fragment then writes current-minus-previous normalized screen UV motion. The history snapshot is presentation-only; the animation and authoritative simulation aren't modified. This path intentionally skips baked + morph simultaneous deformation until a mixed permutation is available.

An optional alpha-cutout rigid velocity variant now replays the material's base texture alpha cutoff with KHR texture transform (offset/scale/rotation), base alpha and vertex-color alpha (when enabled). Because cutout surfaces contain empty pixels, the dedicated variant samples the base alpha texture and discards rejected fragments before depth-occlusion testing. These materials are kept out of the ordinary opaque instanced velocity draw and rendered separately. ShaderGraph-displaced surfaces and deformable alpha-cutout models are not included, since their visible shape requires matching additional material stages. Fully blended/transparent models remain excluded.

The rigid history now stores the source Model identity alongside its world transform, preventing a reused persistentId from picking up a different model's previous transform. Existing per-view reset, initial frame and resize behavior stays intact.

motionBlur also accepts depthThreshold (default 0.012, range 0.0005..0.05) for rejecting unrelated depth layers during the directional color gather. The shader falls back to the sharp sample if all gathered samples are rejected instead of blending black into the image. The threshold is in non-linear device depth units, not metres. Example:

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012}

All additional paths remain behind the pre-existing AIVERSE_PRISMA_MOTION_BLUR=1 and HDR/quality gates. They use the same masked velocity texture bridge and do not change gameplay ECS or SpectraFX. Stage 29 — camera-cut epochs, reactive transparency and baked+morph velocity#

PRISMA's experimental HDR motionBlur path now has three additional presentation-only capabilities, all gated by the existing AIVERSE_PRISMA_MOTION_BLUR=1 runtime flag and configured quality.

Explicit camera/view lifecycle. Prisma::resetMotionHistory(viewId) increments a monotonically increasing per-view camera-cut epoch exposed by PostProcess::objectMotionEpoch(viewId). Renderer3D reads this epoch on each opt-in velocity pass and discards prior rigid and deformable transform snapshots when it changes. This keeps the camera reprojection and per-object pose histories in sync across camera cuts, teleports, quality changes and map reconfigurations without modifying gameplay ECS. The renderer also provides resetObjectMotionHistory(viewId) and resetAllObjectMotionHistory() for explicit standalone control. releaseObjectMotionViewAfterGpuIdle(viewId) releases the per-view GPU velocity, reactive and depth textures only after the host has confirmed GPU idle; CPU frame serials are NOT a GPU completion signal. No automatic viewport closure or backend GPU fences are wired yet.

A new read-only Renderer3D::objectMotionStats() returns the last velocity pass's view ID, submitted state and rigid instance/draw, cutout, skinned, baked, reactive and rejected draw counters. These values are CPU submission diagnostics, not measured GPU time or performance data.

Reactive masks. Renderer3D can emit a separate, current-frame RGBA8 reactive coverage texture for visible rigid, translucent ModelDraw primitives. It samples the final scene depth and uses a dedicated scratch depth attachment rather than modifying scene depth. The red channel is coverage strength, while an all-zero background means no reactive pixels. PostProcess::acceptMotionReactiveMask forwards the borrowed handle to PRISMA. Native renderers can instead provide a borrowed R=0..1 texture through Prisma::setMotionReactiveMask(viewId,texture) before resolve. The motion blur shader samples this mask at texture slot 3 and reduces local blur strength by 1 - reactive * reactiveStrength. A missing mask uses the black fallback, so motion blur remains unchanged.

The new optional effect parameter reactiveStrength defaults to 0.85 and has a range of 0..1. The renderer's reactive pass is a conservative geometric silhouette of translucent rigid models: it does not reproduce per-pixel blended texture alpha, alpha-test materials, skinning, particles or water drawn by other renderer modules. False-positive reactive coverage may reduce blur inside glass geometry, which is preferable to inventing object velocities. It remains an experimental approximation.

Baked clip + morph. The baked-velocity vertex shader now applies both the current and previous morph weights against immutable morph deltas (tex8) before sampling current and previous baked clip rows from tex7, matching the existing color shader's deformation order. Palette, animation and morph parameters are all per primitive and per view; a missing previous frame or changed model identity still suppresses object-velocity override. This does not add per-vertex CPU readback or change deterministic animation state.

LOD transition geometry that requires screen-space dithering is now conservatively excluded from object velocity until a matching LOD fade shader is implemented; camera motion reconstruction remains the fallback there.

Example:

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012,
 "reactiveStrength":0.85}

Stage 30 — animated reactive coverage, extensible water/particle masks, LOD fallback and velocity dilation#

The existing experimental motionBlur chain now supports animated, current-frame reactive coverage for translucent skinned, morph and baked-clip ModelDraw geometry. These reactive passes do not invent previous animation poses or feed object motion velocity: they evaluate the current GPU-deformed vertex position using the same vertex path as the Stage 27/29 motion shaders, sample the read-only scene depth for visibility, and mark covered pixels as reactive (R=1). The animated Metal shaders reuse the established skinned/baked vertex shader source while substituting a coverage-only fragment. This handles baked+morph current-pose silhouettes, but does not reproduce per-pixel transparent material alpha, ShaderGraph vertex displacement, screen-space water, or particles automatically. These may be more accurately supplied by the owning renderer.

Reactive coverage extension for all renderers#

Renderer3D::addMotionReactiveDraw(fn) registers a presentation-only, current-scene callback with signature

void(gfx::Device& device, gfx::TextureHandle sceneDepth,
     int width, int height)

Register after beginScene() and before resolvePrisma() (typically after the main scene/color pass has been submitted); callback registration is cleared automatically after the current scene's resolve. The callback is invoked inside an already open RGBA8 reactive render pass with a separate scratch depth target; it must never call beginPass/endPass. The provider binds its own shader, geometry, texture/constant state and writes red channel R in [0,1] (0 = no reaction, 1 = suppress blur according to the configured strength). Use coverage-union-friendly blending, such as gfx::BlendMode::Screen, so several water/particle/object providers combine rather than erase one another. Built-in reactive pipelines now use Screen blending for accumulation of multiple overlapping masks. This is coverage-aware blur suppression, not full motion-vector reconstruction across LOD changes.

The new motionBlur.velocityDilation parameter (default 1.0, range 0..2, 0 disables) samples four neighbouring velocity values at the requested radius, selecting a stronger velocity only when its device-depth closely matches the center pixel. This helps preserve motion around silhouettes without importing motion from clearly different depths. It is a local approximate depth check (hardware depth units, not metres) and costs up to four additional velocity and depth reads per blurred pixel. The cost estimator includes this additional work when enabled.

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"depthThreshold":0.012,"reactiveStrength":0.85,
 "velocityDilation":1}

This API performs no GPU readback and does not make input textures globally self-describing when passed outside the RHI.

Safe handoff for retiring old motion targets#

The manual retireObjectMotionView(viewId,lastSubmittedFence) transfers one view's current targets to this queue and discards its CPU history.

If the renderer has no valid submission fence, old targets are put into an unfenced quarantine, where they are retained until drainObjectMotionAfterGpuIdle() is called with a proven idle GPU. Normal engine shutdown currently assumes the host has reached its existing safe teardown point. There is no automatic backend fence emission or polling yet, so this conservative default can retain GPU memory across many viewport resizes until idle. CPU frame counters and arbitrary N-frame delays do not count as GPU fences.

The older releaseObjectMotionViewAfterGpuIdle remains a separate synchronous API and must only be invoked after the GPU is idle. These changes do not automatically repair unrelated PRISMA Sized pool or other rendering-resource release points; those require their own GPU-completion-aware integrations.

Stage 33 — GPU-completed fences for safe PRISMA resource retirement#

The renderer now exposes a separate GPU-completion timeline in the genre-independent gfx::Device interface:

uint64_t submitted = dev.gpuSubmissionFence(); // current GPU frame, 0 if unavailable
uint64_t completed = dev.gpuCompletedFence();  // GPU-confirmed completion only

The submitted token covers work encoded in the currently active GPU frame and is not the CPU frame counter. It can be attached to a target retirement before that frame is actually submitted; the backend will complete it only after GPU execution. A nonzero gpuCompletedFence() result is a real, contiguous completed GPU timeline token. Unsupported devices return zero. All values are per-device; never compare values from different devices, contexts or GPU queues.

Metal: GfxMetal.mm uses the current command buffer's frame token and updates an atomic completed counter in its addCompletedHandler only for MTLCommandBufferStatusCompleted. It does not turn frameSerial() into a completion fence. The asynchronous callback captures shared lifetime-safe state and the graphics owner thread polls it by reading gpuCompletedFence().

GL33 / GLES3 / WebGL2: after the frame's render commands the backend inserts glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE,0) and flushes the command stream without waiting. At the next beginFrame, it calls glClientWaitSync(..., timeout=0) on its oldest pending fence, advancing completed tokens strictly in submission order and deleting signalled GL sync objects. The Windows GL33 dynamic loader now loads glFenceSync, glClientWaitSync, glDeleteSync. A failed fence is never treated as successful completion. No per-frame glFinish is added.

Vulkan: uses its already existing per-frame VkFence and serial_. gpuSubmissionFence is the currently recording GPU frame's serial; gpuCompletedFence returns only the highest serial whose slot fence has been successfully confirmed by vkWaitForFences. A lost device or unsuccessful wait does not advance the completed fence. This is the existing slot-wait path, not a new polling implementation that blocks extra frames.

Automatic motion target reclamation#

Renderer3D::beginScene now calls collectCompletedObjectMotion(dev.gpuCompletedFence()) on the graphics owner thread. When a viewport changes size, queueObjectMotionTexture takes the current dev.gpuSubmissionFence() if available and associates it with the old object velocity, reactive or scratch-depth target. On completion the old targets are destroyed; before then they are retained. retireObjectMotionView and setObjectMotionSubmittedFence remain available for externally managed submission lifecycles. On devices without submission-fence support, old targets remain in the Stage 32 quarantine until explicit GPU idle.

Deferred PRISMA Sized / RenderGraph targets#

Prisma::sized still keeps three active size entries for Scene/Game views, but when evicting the least-recently-used entry it now moves the whole Sized context — legacy raster targets, depth targets, cached Bloom graph and persistent PrismaRhiExecutor resource pool — into a fence-tagged retirement list instead of releasing it immediately. When the GPU reports that the last referencing submission completed, collectCompletedSizes frees the retired targets and safely resets the graph executor pool. In addition, Prisma::target now fence-retires targets replaced by size/HDR format changes, avoiding immediate destruction of a texture that may be in use by an earlier in-flight GPU command buffer.

Prisma::releaseRetiredSizesAfterGpuIdle() is the escape hatch for hosts that have explicitly waited for an idle GPU; the function also drains unfenced/quarantined individual targets. The shutdown path assumes the platform's normal device-teardown GPU-idle condition.

This stage is about resource lifetime correctness, not a change to image output, bloom topology, exposed postfx JSON, particle simulation or gameplay ECS. Existing experimental flags remain off by default.

Limits#

The new timeline only covers commands on the backend's regular graphics submission queue. External GPU queues or devices need their own fence tracking. Metal handles are released after the command buffer completion callback; GLES/WebGL sync capabilities and actual device behavior still require runtime validation. Vulkan may only advance its completion counter when rotating to a frame slot whose fence was waited. Without a GPU-completed token, retired resources are not released opportunistically and quarantine can grow.

Auto Exposure per-view 1×1 history, PRISMA LUTs, externally owned Sprite/FX buffers and other unrelated render-resource caches have their own existing teardown policies; they are not all migrated to this queue. RenderGraph internal pool cleanup is deferred together with the evicted Sized context, rather than by assuming every pixel pass finished at the end of the CPU frame.

Stage 35 — editor framebuffer GPU retirement and explicit pressure drain#

The editor's actual Viewport::color and Viewport::depth render targets now use the same GPU-completed-fence principles as PRISMA and Renderer3D. They are not owned by PRISMA: a new apps/editor/ViewportGpuRetirement.h owner lives in the Editor instance and outlives its Scene/Game/FX window objects. Viewport binds that owner during ensure(dev,w,h,owner), and release() / resize / viewport destruction transfer both GPU handles to the owner instead of directly destroying in-flight images.

The old color handle may still be in an ImGui draw command even after the window's Viewport::image() returns, so it is only destroyed after gfx::Device::gpuCompletedFence() covers the submission that may reference it. Unfenced resources are quarantined until the host has explicitly verified GPU idle. The owner also clears the viewport's stale drawnFrame / hover state when released.

All three editor producers (Scene, Game and FX windows) use this shared owner. They release hidden/closed offscreen render targets without relying on window destruction; the owner retains resources past window lifetime. A hidden/closed tab can later recreate a framebuffer with no stale ImGui texture handles.

Memory pressure policy#

ViewportGpuRetirement reports pending fenced/unfenced texture counts, metadata-derived knownPendingBytes, a threshold and an overBudget indicator. The default shared known-pending budget is 128 MiB, configurable through AIVERSE_PRISMA_RETIRE_BUDGET_MB (32..4096 MiB). The editor checks the sum of known pending bytes from Viewport, PRISMA and Renderer3D on the pre-render boundary of Editor::frame, before any new GPU draw submission. It normally collects already GPU-completed resources with no wait.

If that known pending memory exceeds the budget, it can call the new explicit gfx::Device::waitForSubmittedGpuWork() hook exactly at that safe point. On successful synchronization it drains the Viewport, PRISMA and Renderer3D GPU retirement queues, including unfenced quarantine. It never releases an in-flight texture based on the number of elapsed CPU frames.

This explicit pressure-only wait is implemented with glFinish() on GL33/GLES3 (excluding WebGL), waiting the last actually committed Metal command buffer (never the uncommitted buffer for the current frame), and vkQueueWaitIdle on Vulkan. These waits are not performed every frame; they can cause a visible one-time stall at memory pressure. The WebGL2 backend explicitly returns false because a portable synchronous idle barrier is not promised; resources remain quarantined until an external safe teardown. A positive wait result only covers previously submitted GPU commands, so the editor must call it before it encodes new frame work that uses those resources.

The Statistics tab now shows viewport fenced/unfenced resource counts, known pending MiB versus the configured budget, and a "Запросить безопасную очистку GPU" button. That button merely requests a one-shot cleanup at the next frame's pre-render boundary, not while the Statistics window's ImGui pass is active.

The threshold is an advisory pressure budget rather than a global hard GPU VRAM cap. Internal RenderGraph allocations, active resources, driver overhead, and unknown/unsupported RHI texture descriptors may not be included in the lower-bound estimate. If a backend cannot synchronize, the editor deliberately retains memory rather than risking GPU use-after-free.

The RHI's prior gpuSubmissionFence() / gpuCompletedFence() APIs are unchanged, and the new waitForSubmittedGpuWork() is optional. All postprocessing flags remain off by default; no ECS/gameplay ownership changes.

Stage 37 — generic GPU-fenced shaders, pipelines, buffers, FX hot reload#

Stage 37 extends the GPU-completion lifetime policy from textures and viewport resources to all RHI handle categories used by Shader Graph and VFX hot reload.

engine/render/GpuResourceRetirement.h introduces a genre-independent, graphics-owner-thread lifetime service with overloads for gfx::PipelineHandle, ShaderHandle, BufferHandle, TextureHandle, and ComputeHandle. Each retired handle is detached from its old owner and stored with the GPU submission token from gfx::Device::gpuSubmissionFence(). A zero token is quarantined. A verified gpuCompletedFence() allows nonblocking reclamation; explicit drainAfterGpuIdle() requires a real GPU-idle guarantee.

When multiple GPU handles become eligible at the same time, the service destroys pipelines before shaders, preserving dependencies. It also supports retireOwned(device,cleanup,knownBytes) for complex rendering-owner bundles whose internal destruction order is already encapsulated. The callback is invoked only after GPU completion on the graphics-owner thread, never from the Metal completion-handler thread. The service tracks pending resource-type counts, fenced/unfenced entries and optional known bytes; these are lower bounds, not complete VRAM metrics. It owns resources exclusively; do not hand it borrowed handles.

The Shader Graph editor now retains the entire previous ShaderGraphPreview object on a graph asset/project/domain change. The archived object includes its Portrait/Renderer3D, ParticleSystem, PRISMA, TextureCache, shaders, pipelines, vertex buffers, and preview color/depth targets. The new preview is created separately. The old preview's shutdownAfterGpuCompletion() runs only when its last GPU submission fence has actually completed (or at explicit GPU idle). This avoids the former immediate pipeline/shader destruction while a previous GPU frame may still reference those resources.

A UI-only change to the node position field does not invalidate GPU shader preview resources; both the window and preview use a shared ShaderGraphPreview::resourceKey(graph) that excludes node screen positions. Stage 42 — opt-in HDR temporalResolve (full-resolution history reprojection)#

This feature extends the existing canonical Prisma pipeline, not the historical PrismaScreenLighting wrapper. Existing effect IDs, postfx JSON roots, saved panel ID, and PostFx compatibility headers remain unchanged.

Prisma::resolve() now reuses a single full-resolution signed velocity pass for both Temporal Resolve and Motion Blur, if requested. Stage 43 — optional subpixel jitter and confidence-aware temporal AA#

Stage 43 builds on Stage 42's canonical PRISMA temporalResolve without introducing a second TAA subsystem or rewriting stable postfx/MCP identifiers. The native-resolution history remains two per-camera HDR RGBA16F targets; no lower-resolution render target or temporal upscaler is introduced.

The effect adds two optional float parameters:

  • jitterPixels: 0..0.5 (default 0.5) controls the maximum subpixel projection offset. Jitter additionally requires AIVERSE_PRISMA_JITTER=1 and the original AIVERSE_PRISMA_TEMPORAL=1, with HDR + High quality and an authored enabled temporalResolve effect. Existing games are unmodified without both explicit environment flags.
  • historyConfidence: 0..1 (default 0.65) controls how aggressively previous HDR color is rejected near sharp luma/depth changes, in addition to the Stage 42 disocclusion depth/velocity/reactive rules.

C++ camera contract: Call setViewId(id), then applyCameraVolumes(stack, camera.eye()), then RTSCamera renderCamera = prisma.jitteredCamera(camera,w,h) immediately before renderer.beginScene(renderCamera,w,h). jitteredCamera returns a copy and never mutates camera itself: keep the original RTSCamera for mouse picking, editor gizmos, UI, and touch input. The standard GameClient, Editor Scene and Editor Game rendering paths have been updated to follow this sequence. ShaderGraph, FX and native preview owners may opt in separately. The real render projection uses RTSCamera::jitter, and the renderer's shadow-camera strips jitter already, avoiding artificial shadow-map projection shifts.

Shader behavior: Each view ID maintains its own 8-step Halton (2,3) sequence. Jitter is expressed in NDC by the camera; the temporal shader receives the current/previous jitter in unflipped normalized UV. Each stable output pixel samples the current HDR color/depth/velocity at pixel + currentJitter, then samples the prior history at reprojectedInputUV - previousJitter. This removes projection jitter from the history-addressing and from physical-motion confidence while retaining distinct subpixel samples for accumulation. GLSL and Metal use the same shader body, with the render-target Y flip applied only by the existing TUV macro. A 3×3 current compressed-HDR color neighborhood yields local mean/variance and bounds; the shader uses independently depth-validated previous taps, color disagreement and current depth-edge contrast as confidence multipliers. Moving silhouettes and reactive particles therefore receive lower history weight than smooth static surfaces.

On explicit camera cuts, projection type/FOV/near/far discontinuities, history changes, jitter mode/amplitude switches or viewport size changes, the temporal history restarts instead of blending incompatible pixels. The existing camera-position cutoff still applies. PrismaStats reports whether the last frame resolved temporal color, whether jitter was active, and the applied offsets in pixels; the PRISMA — Постобработка panel displays the values.

This is native-resolution temporal antialiasing, not jittered temporal upscaling, DLSS/FSR/TSR, optical flow or dynamic-resolution rendering. Transparent surfaces and screenspace effects may still alias if their producers do not supply suitable reactive or motion masks. PrismaScreenLighting contains an older optional independent TAA; do not activate both histories at once. The history and GPU-referenced resources remain subject to GPU-fence retirement from Stages 35–42.

Stage 44 — explicit internal render resolution and temporal upscaling#

Stage 44 extends the canonical opt-in temporalResolve / Halton TAA path with a true internal 3D render resolution that may differ from the final output target. It adds two catalog parameters to the existing postfx.effects[{type:"temporalResolve"}] payload:

  • renderScale (0.5..1, default 1): fraction of the output width and height used by 3D, depth and motion-vector passes. The chosen scale is quantized to 1/16 steps; actual pixel counts are rounded, bounded to 32px minimum and require at least 64px output dimensions.

The feature is disabled unless all three flags are explicitly set: AIVERSE_PRISMA_TEMPORAL=1, AIVERSE_PRISMA_JITTER=1 and AIVERSE_PRISMA_UPSCALE=1. An enabled temporalResolve authored in the normal game/map postfx catalog, HDR support, High quality, historyWeight>0, jitterPixels>0 and renderScale<1 are also required. Existing projects and low/medium/mobile quality tiers retain 1:1 rendering by default.

Host call order: after setViewId(id) and applyCameraVolumes(stack,camera.eye()), call auto [renderW,renderH] = prisma.renderSizeForOutput(outputW,outputH) and then prisma.jitteredCamera(camera,renderW,renderH). The temporal pass runs immediately before final color composite and writes a viewId-private output-resolution RGBA16F history (RGB linear HDR, A prior hardware depth). Motion vectors remain current-minus-previous in normalized screen UV, so their coordinates do not require ad-hoc multiplication by the resolution ratio. The shader applies Stage 43 jitter correction, four individually depth-validated previous history taps, current luma/depth confidence, reactive coverage and bounded HDR sharpening. Final tonemap/composite and optional full-resolution UI remain output-size. HD/SDR FXAA is not layered over a successful HDR temporal resolve.

Old targets go through the existing GPU-fence retirement rather than immediate destruction. Stage 45 — GPU-sampled adaptive resolution and pre-render stable fallback#

This stage extends the opt-in Stage 44 source/output temporal scale path. It does not change any defaults or the postfx JSON root, existing MCP IDs, editor tab ID, scene shaders or genre-specific simulation.

New effect controls in the existing temporalResolve catalog: adaptiveResolution (boolean, defaults false), targetGpuMs (4..50ms, default 16.6) and minRenderScale (0.5..1, default 0.5). The authored Stage 44 renderScale remains the quality ceiling and cannot be exceeded by the adaptive controller. To opt in, set AIVERSE_PRISMA_ADAPTIVE=1 in addition to all three Stage 44 flags (AIVERSE_PRISMA_TEMPORAL=1, AIVERSE_PRISMA_JITTER=1, AIVERSE_PRISMA_UPSCALE=1), choose HDR/High and author an enabled temporalResolve effect with adaptiveResolution:true.

PrismaAdaptiveResolution is a CPU-only, genre-independent policy in engine/render/PrismaAdaptiveResolution.h. It consumes only finite, positive, asynchronously completed Device::gpuFrameMs() readings from new, strictly increasing Device::gpuCompletedFence() tokens. A backend without reliable results (e.g. unsupported GL/Vulkan) stays at the authored scale; the policy never substitutes editor CPU frame time, FPS, frame serials or predicted GPU timings. On Metal the signal measures the whole GPU command frame, not an isolated Prisma pass or editor view; adapting multiple editor views to the same whole-frame measurement is conservative and can shift quality in both.

Hysteresis: GPU duration above 115% target for 12 distinct completed samples causes a 1/16 renderScale decrease; GPU duration below 80% target for 36 samples causes a 1/16 increase, up to authored ceiling. A changed scale starts 48 completed samples of cooldown, reducing rapid resize/reallocation loops. The floor and ceiling are clamped and quantized; Prisma::retireView removes per-view controller state when the viewport is closed.

Pre-render resource preflight: renderSizeForOutput() on the graphics thread now calls preflightUpscale() before returning any internal resolution smaller than the output. It checks the temporal and motion GPU programs, the guaranteed fallback composite, the HDR RGBA16F size-owned scene/velocity textures, internal scene/depth/scratch, the camera-private pair of output-size HDR temporal histories and the output-size scratch depth. History reallocations use existing GPU-fenced retirement. A failed preflight returns full input/output dimensions and inhibits jitter for that view. Allocation retries are rate-limited (60 render-size queries) so an unsupported or memory-constrained device is not hammered each frame. No GPU wait is introduced in this path.

Jitter-safe runtime fallback: if a temporal pass unexpectedly cannot run after a low-resolution jittered scene was already encoded, the final compositor uses graphFrame.zw as a current-jitter sampling offset s + currentJitter for source color and dependent screen effects. The offset is zero during a successful temporal resolve or normal non-jittered presentation. That keeps the fallback image on a stable output pixel grid while still allowing linear bilinear upscaling and HDR color processing. This is a visual stabilization measure, not a guarantee of production image quality or a replacement for real temporal accumulation. HUD and input remain full-size and unjittered.

PrismaStats adds adaptiveResolution, requestedRenderScale and temporalFallback; the existing PRISMA editor panel displays them alongside output/internal resolutions and optional asynchronously completed whole-frame GPU milliseconds. No precise GPU time is shown if unsupported.

Limitations: backend timing may be absent; whole-frame timing includes other GPU jobs; the fallback can still exhibit simple bilinear aliasing and thin-edge shimmer; a mid-frame device loss cannot be recovered with texture sampling; cached allocation pressure may temporarily rise around scale transitions until actual GPU-completed fences allow reclamation. Adaptive scaling does not synthesize true per-viewport GPU timing nor promise a frame-rate gain. Motion-vector reprojection, jitter sign and GLSL/MSL compilation still need native GPU validation.

Stage 46 — actual scoped GL33 viewport GPU timings and VRAM-pressure guard#

The timing distinction matters: RHI gfx::Device now has optional nonblocking beginGpuScope(tag)/endGpuScope() and a separate takeGpuScopeTimings() result queue. Unlike gpuFrameMs() and timeGpuFrame(), a scope measures only GPU commands submitted between its boundaries. Desktop OpenGL 3.3 on supported macOS/Windows paths uses a real GL_TIME_ELAPSED query. The backend refuses to start a scope while a whole-frame elapsed query or another scope is running (OpenGL does not allow nested same-target queries). takeGpuScopeTimings() only returns completed, nonblocking results and does not consume other takeGpuTimings() benchmark results. The bounded queue is capped at 64 pending entries. GL ES/WebGL/Linux fallback, Metal and Vulkan do not claim per-viewport timings: the default API returns false/empty. Metal's gpuFrameMs() is whole-command-buffer duration and must always be labeled as such.

Editor opt-in: AIVERSE_PRISMA_VIEWPORT_GPU_TIMING=1. For Scene/Game, the editor begins a GPU timing scope immediately before the graphics Renderer3D::render and ends it after Renderer3D::resolvePrisma and the last viewport pass. This covers rendered shadows, world, post-effects and scene FX in this interval, not prior CPU scene preparation, prior GPU asset streaming or other windows. When supported, the editor polls finished measurements at its pre-render safe boundary, passes them to Prisma::acceptViewGpuTiming(viewId,gpuMs) and lists per-viewport samples through Prisma::viewGpuTimings(). The source is presentation/diagnostic only, not the authoritative simulation or an ECS component. It is opt-in and never enables full-frame timing automatically.

Adaptive source selection: the existing PrismaAdaptiveResolution controller now prefers the latest completed scoped GL query for its particular view. Each accepted scoped query increments that view's completed-sample sequence; a repeat value cannot cause repeated hysteresis updates. If no scoped query is available, the controller retains the earlier whole-GPU-frame fallback gated by the genuine Device::gpuCompletedFence(). It does not convert CPU FPS to GPU milliseconds. Scoped interval duration still includes shared GPU shadow/reflection/FX passes and is not a pure postprocess-only cost. On unsupported backends this scope-specific diagnostic is explicitly unavailable.

These estimates count shared size-cache allocations once, add active per-view HDR histories and pending fence-retired textures exactly once, and exclude unknown/unobservable bytes and physical driver overhead. A known lower-bound overage counts as a pressure sample only on a new confirmed GPU completion (actual completed scope query or GPU fence). After 12 over-budget samples it may step scale down 1/16. Over-budget pressure blocks upward quality steps; normal fast/slow GPU timing and the existing 48-completed-sample cooldown continue to apply. Pressure alone does not allow unsafe GPU release, unconditional memory waits, or repeated CPU-frame counting. Without a verified GPU completion, no adaptation is attempted.

PrismaStats and the editor report the chosen timing source, last valid GPU milliseconds, known Prisma live+pending bytes, the configured threshold and whether it is exceeded. The Stats window also displays the recent completed GL33 Scene/Game intervals, rather than mislabeling Metal whole-frame timings as isolated view costs.

The memory threshold is not total physical VRAM or a hard memory cap, and unmeasurable ShaderGraph/Portrait/driver allocations remain unknown. Over-budget known bytes may stay high until actual fence completion; bounded frame hysteresis prevents per-frame thrashing, but is not a promise of performance gain. Stage 47 — Metal hardware-scoped timings, renderer-owned memory and trustworthy source switching#

Per-camera policy API in Prisma.h:

prisma.clearViewQualityPolicy(viewId);

The policy is independent of FPS/RTS gameplay, UI input and GPU resource ownership. Priority is an integer from 0 (yield first) to 255 (yield last), with default 128. Under known GPU memory pressure alone, the hysteresis controller requires 6 completed samples for low priority (0..84), 12 for normal (85..169) and 30 for high (170..255) before a downward 1/16-scale step. A genuinely over-budget GPU frame time still causes a downgrade after the existing 12 completed samples for every priority, and fast recovery needs 36 valid samples. Each resize has its existing 48-completion cooldown, avoiding oscillation.

maxTemporalHistoryMiB==0 means no camera-specific admission cap. A positive value limits ONLY the two per-view full-output RGBA16F histories: 2*outputWidth*outputHeight*8 bytes. Before any scene is jittered, renderSizeForOutput rejects an upscale whose required output-history size exceeds that view's quota, returns full native render dimensions and fence-retires previous history allocations. Rejection is propagated through jitteredCamera AND Prisma::resolve; the latter must not allocate histories that were refused during admission. Thus a rejected view presents ordinary full-resolution output with stable camera projection, not a jittered scene without a valid temporal pass. PrismaStats reports priority and admission status. retireView erases the policy and rejected flag, preventing stale hidden camera settings from leaking into a replacement view.

Default host choices in this stage: Editor Scene priority 64 with 128 MiB for the pair of HDR histories; editor Game and GameClient use priority 224 with 256 MiB history cap. Other native project hosts may supply custom policies. The global memory-pressure budget, the per-view history admission limit and runtime GPU-scoped timings each control separate decisions and must not be conflated.

Stage 55 — Auto Exposure совместно с четырьмя Shader Graph текстурами#

До этого этапа PRISMA отводила для GPU HDR Auto Exposure фиксированный sampler TEX8, а postfx Shader Graph использовал привязки TEX5..TEX8 для максимум четырёх независимых текстур. При четырёх текстурах включённая автором Auto Exposure молча отключалась, хотя все остальные её условия были выполнены. Это было функциональным ограничением, а не физическим запретом RHI.

Новый GPU-независимый PrismaCompositeTextureLayout.h определяет общую, constexpr-вычислимую карту ресурсов. Фиксированный композит занимает слоты 0..4, Shader Graph — 5..8, а HDR Auto Exposure — слот 8, пока граф использует 0..3 текстуры, и слот 9 при четырёх текстурах. Неподдерживаемое количество текстур (более 4) явно отклоняется. Пять static_assert подтверждают ожидаемые вычисления при компиляции библиотеки; нативная компиляция ещё НЕ проводилась. Схема не меняет сериализацию, JSON или MCP API.

В Prisma.cpp план используется одновременно при создании ShaderDesc.textureSlots, формировании masks для GLSL/MSL TEX0..TEX9 и фактическом Device::setTexture. PrismaShaders.h выбирает TEX9 только с PF_AUTO_EXPOSURE_SLOT9, иначе сохраняет TEX8. Ключ кэша composite остаётся effectMask + ShaderGraph JSON: этого достаточно, поскольку layout однозначно определяется самим графом. При ошибке построения expanded pipeline PRISMA сохраняет старый fallback: тот же composite без Auto Exposure, а если он тоже недоступен, базовый composite без эффектов. Не подменять неуспешный pass на «эффект выполнен».

Prisma::ViewEffectReport теперь содержит shaderGraphTextures и autoExposureTextureSlot. Последнее равно -1, когда финальная выбранная composite pipeline не содержит Auto Exposure; запись обновляется только после разрешения fallback. Editor PRISMA — Постобработка показывает фактический slot по каждому viewId, не инициируя GPU shader compile для отображения диагностики.

Это структурная оценка исходников, не доказательство работоспособности на всех адаптерах GLES/WebGL/Metal/Vulkan.

Stage 56 — Depth of Field: фокус по расстоянию и защита силуэтов#

Экспериментальный depthOfField остаётся частью PRISMA и по-прежнему требует AIVERSE_PRISMA_DOF=1 и подходящий quality tier. Старые карты/JSON автоматически используют прежний режим: focusDepth и focusRange в аппаратной глубине [0,1]; maxBlur и intensity остаются без изменений. В shader этот режим сохранён в отдельной ветви с оригинальной формулой и 10-весовой схемой размытия, чтобы старое изображение не переинтерпретировалось как физическое расстояние.

Новые необязательные параметры того же эффекта:

ПараметрПо умолчаниюНазначение
metricFocusfalseЯвно включить линейную глубину по данным камеры
focusDistance12Плоскость фокуса вдоль направления взгляда (единицы мира)
focusRangeMeters4Интервал резкости вокруг плоскости фокуса
occlusionToleranceMeters0.35Допустимый перепад глубины между центром и tap до подавления смешивания

Обозначение «метры» относится к проектам, где одна единица мира равна метру. Это линейная глубина вдоль направления камеры (view-space Z), не сферическая дистанция от глаза до произвольной точки. Для perspective: z = near * far / (far - depth * (far - near)); для orthographic: z = mix(near, far, depth). Renderer3D::resolvePrisma() уже передаёт PostFrame.depthNear, depthFar и orthographic; ортографические границы текущего renderer могут быть отрицательными -200..1000, что корректно поддерживается.

Код Prisma.cpp проверяет finite near/far и far > near; perspective также требует near > 0. Если metricFocus запрошен, но входная проекция невалидна, RHI draw выполняет старую аппаратную глубину, а Prisma::EffectExecution для этой камеры выставляет encoded=true, degraded=true и конкретный reason. Это предотвращает NaN и пустой кадр. Указатель на report остаётся read-only; degraded не означает проверенную визуальную корректность эффекта на GPU.

Metric-шейдер считает CoC из линейной глубины и в восьми соседних цветовых tap выбирает вес по разнице линейной глубины. Точки, отделённые силуэтом или принадлежащие sky/background (device depth >= 0.99999), не смешиваются, переход между согласованными и несогласованными слоями сглажен smoothstep. GPU sampling оставлен в linear HDR; output alpha в metric-ветви наследуется от исходного SceneColor. Legacy-ветвь оставляет прежний output alpha=1 по совместимости. Самплируемый scene depth никогда не привязывается как writable depth attachment; для DoF используется отдельный scratchDepth. Pass работает с src.tex, который может содержать результат предыдущего Motion Blur, и теперь проверяет наличие именно src.tex перед draw.

PrismaData.cpp автоматически открывает новые поля в общей схеме JSON/editor/MCP/volume-mask; отдельную реализацию для FPS, RTS или SpectraFX не создавать. В PrismaWindow.cpp добавлена подсказка о выборе режима и видимое degraded fallback в матрице эффектов по viewId. Любой старый postfx без metricFocus продолжит использовать старый путь.

Ограничения: это 8-tap screen-space defocus, а не физически правильный bokeh, Gather/Scatter DoF или полноценное separated foreground/background scattering. На пересечениях полупрозрачных поверхностей ограничение глубиной может подавлять размывание, но не может восстановить закрытые за объектами цвета. Семантика depth [0,1], камера и Metal/GL parity требуют проверки на реальном устройстве.

Stage 57 — устойчивый HDR Auto Exposure и согласованный camera-cut reset#

autoExposure по-прежнему требует эффекта в postfx-профиле, эффективного HDR и переменной AIVERSE_PRISMA_AUTO_EXPOSURE=1. Измерение яркости остаётся в линейном scene-referred HDR до тонмаппинга и UI, а его отдельная 1×1 ping-pong history принадлежит стабильному viewId, независимо от размеров Scene/Game viewport.

Новые необязательные параметры общего PrismaData-каталога:

ПолеDefaultДиапазонЗначение
highlightRejection00..0.95Насколько уменьшать влияние очень ярких пикселей при измерении
highlightStartEV3-10..16Порог начала снижения веса в log2(luminance), а НЕ camera exposure EV
highlightSoftnessEV20.1..8Плавность перехода до максимального снижения веса в ступенях log2

highlightRejection=0 по умолчанию сохраняет прежний weighted log-luminance estimator и уже существующие centerWeight, centerRadius, minMeterLogL, maxMeterLogL, EV clamps и скорости адаптации. Это опциональный soft highlight weighting, не histogram/percentile metering.

GPU shader kExposureLog вычисляет luminance каждого из четырёх семплов, ограничивает logL текущими minMeterLogL/maxMeterLogL, затем уменьшает базовый пространственный вес: weight *= 1 - rejection * smoothstep(startEV, startEV+softnessEV, logL). Граница rejection <= 0.95 гарантирует не менее 5% исходного веса даже для полностью яркого кадра и исключает нулевой знаменатель измерения. Пирамидальное уменьшение kExposureReduce по-прежнему отдельно переносит взвешенную сумму log2 luminance и сумму весов, а kExposureAdapt делит первое на второе перед вычислением EV. Нет скрытого GPU readback или CPU luminance pass.

Camera cut: до Stage 57 обнаружение автоматического скачка камеры происходило после GPU-метеринга, поэтому первый кадр после телепорта мог смешиваться с прежней экспозицией. Теперь проверка motionView.previousCameraPos, finite и скачка свыше 12 единиц мира выполняется в начале Prisma::resolve до Auto Exposure. Сброс одновременно инвалидирует velocity/temporal history и resetAutoExposure(viewId_). Явные resetMotionHistory(id) / resetMotionHistory() также инвалидируют per-view/all-view exposure history без удаления GPU текстур. Первый адаптационный pass новой камеры использует historyValid=false и заново инициализируется от текущего измерения. Сброс не требует ожидания GPU и не путает две камеры одного разрешения.

Цветовой порядок сохранён: weighted HDR metering измеряет scene.tex, 1×1 экспозиция применяется к HDR RGB в PF_AUTO_EXPOSURE внутри final composite, далее ColorGrade-authored exposure в HDR входит в pre-tonemap множитель filt.z, затем ACES/sRGB, пользовательские display-space grade/LUT и postfx Shader Graph. Это два независимых авторских множителя, а не два экземпляра алгоритма автоадаптации; GPU history исключительно одна per-view. Ресурсы Shader Graph (слоты 5..8) и Auto Exposure (8 или 9) продолжают соблюдать Stage 55 layout и fallback без Auto Exposure на неподдерживаемом pipeline.

Prisma::ViewEffectReport теперь записывает autoExposureHighlightRejection только когда финально закодированный composite реально содержит Auto Exposure. Иначе поле остаётся нулевым, autoExposureTextureSlot=-1 и Stage 53 per-effect status указывает отсутствие эффекта. Editor показывает величину и подсказки непосредственно в PRISMA — Постобработка; список эффектов и volume editor получают новые параметры автоматически через общий каталог. Старый postfx JSON, MCP, saved editor panel id и SpectraFX не затрагиваются. Параметры не влияют на authoritative ECS.

Ограничения: не реализованы histogram percentile metering, тональная сегментация кожи/неба, AE metering masks и локальная экспозиция. Глобальный яркий фон всё ещё может влиять на общий результат (не меньше 5%). Настраивать highlightStartEV с учётом scene-referred log2 яркости, а не EV управления камерой. Качество цветовой динамики и GPU shader parity пока не проверены.

Stage 58 — cinematic Exposure Freeze и круговая область HDR metering#

PRISMA по-прежнему использует один глобальный алгоритм Auto Exposure: HDR scene luminance → kExposureLog → kExposureReduce → kExposureAdapt → 1×1 per-view exposure history → final HDR composite до tonemapping/UI. Stage 58 добавляет управление его уже существующими GPU-проходами, без новой ECS-системы, второго шейдерного Exposure owner или обязательных параметров JSON.

Новые необязательные поля postfx.effects[].type=autoExposure#

ПолеDefaultСемантика
freezeExposurefalseУдержать последнее валидное значение 1×1 Auto Exposure этой камеры
meterRegionEnabledfalseВключить локальное взвешивание яркости круговой области кадра
meterCenterX, meterCenterY0.5, 0.5Нормализованный центр области, X слева направо, Y снизу вверх
meterRadius0.25Радиус круга относительно высоты кадра, с поправкой на aspect
meterFeather0.10Плавная ширина края круга, в долях высоты кадра
meterOutsideWeight0.05Вес пикселей вне круга; гарантированно больше 0 (минимум 0.02)

Все поля добавлены в конец прежнего каталога Auto Exposure: старые offsets и значения не сдвигаются. Generic PrismaData parser/serialization, editor, MCP и PrismaVolumeStack автоматически получают новые поля. Для игр без новых ключей прежняя обработка остаётся функционально неизменной; оба режима выключены по умолчанию. Существующий эффект всё ещё требует HDR, соответствующий tier и AIVERSE_PRISMA_AUTO_EXPOSURE=1.

Freeze: при валидной истории ExposureView.history[current] предыдущая 1×1 GPU-текстура просто подключается к final composite. На этом кадре не создаются дополнительные mip targets, не запускаются kExposureLog, kExposureReduce или kExposureAdapt; GPU history не читается и не записывается одновременно. Внутреннее время адаптации обновляется, чтобы разморозка не давала большой delta-time. На первой активной камере, после завершения camera view, сброса настроек или Camera Cut история невалидна; freeze делает один новый метеринг / адаптацию текущей сцены, после чего снова удерживает результат. Явные camera cuts сохраняют контракт Stage 57 — заново захватывать экспозицию, а не навсегда держать прежний кадр. Само выключение эффекта инвалидирует его историю, не уничтожая ресурсы немедленно.

Region: kExposureLog получил дополнительный vec4 region только в собственной UBO (ExposureMeterU). SimpleU и интерфейсы других проходов не изменились. region.z < 0 отключает область без влияния на старую формулу. При включении каждый из четырёх исходных sample UV переводится обратно из backend texture orientation в bottom-up экранные координаты TUV(q); X масштабируется отношением width/height. Веса вычисляются по smoothstep(radius,radius+feather,physicalDistance), после чего перемножаются со старым centerWeight и Stage 57 highlightRejection. Outside weight никогда не равен нулю. Редукция пирамиды сохраняет (weightedLogL, totalWeight) и не зависит от маски; все прочие шейдеры/UBO остаются прежними. Это дешёвое area-weighted metering, не GPU histogram, segmentation, текстурная пользовательская маска или локальная экспозиция по разным частям экрана.

Отдельные настройки для native-камер#

Prisma.h предоставляет GPU-free presentation API, ключованный stable view ID, а не координатами камеры или размером viewport:

prisma.setViewExposureFreeze(viewId, true);
prisma.setViewExposureMeterRegion(viewId, {
    true, 0.5f, 0.5f, 0.25f, 0.10f, 0.05f
});
// Чтобы вернуться к наследованию postfx/PrismaVolumeStack:
prisma.clearViewExposureFreeze(viewId);
prisma.clearViewExposureMeterRegion(viewId);

Также setViewExposureFreeze(id,false) явно переопределяет freezeExposure=true из профиля. setViewExposureMeterRegion проверяет finite и clamping координат, radius, feather и outsideWeight при поступлении. Таким образом две камеры в одной географической точке могут иметь независимые freeze и region параметры. После окончания всех camera passes host передаёт полный набор живых идентификаторов в Prisma::retireUnregisteredViews; новые overrides включены в unionTracked и удаляются retireView/ shutdown вместе с пер-камерным state. Это presentation-only, не authoritative ECS и не изменение глобального базового профиля.

ViewEffectReport.autoExposureFrozen и autoExposureRegionMetered обновляются только если конечный encoded composite реально применяет Auto Exposure. Frozen означает «в этом кадре повторно взята валидная история, meter не запущен»; RegionMetered означает «в этом кадре выполнен замер с областью». При отсутствии exposure в финальном fallback оба false. Окно редактора показывает их по каждому viewId и даёт подсказки по новым generic-полям; GUI-чтение не вызывает GPU-созданий.

Stage 59 — Manual EV, прямоугольная ROI и отказоустойчивый HDR metering#

Ручной EV реализован внутри существующего AutoExposure postfx effect; он не запускает второй HDR owner, GPU-историю, новый fullscreen pass или дополнительный sampler. Каталог PrismaData.cpp дополняет Stage 58 полями:

manualEV0−12…+12 stops, 2^manualEV в линейном HDR

Fixed EV и camera state#

В Prisma::resolve ручной режим выбирается по профилю камеры и native override. При активном manualExposure GPU metering, kExposureLog/Reduce/Adapt, 1×1 exposure history и texture sampler TEX8/TEX9 не используются. Вместо этого уже существующий CompositeU.filt[2] умножается на exp2(manualEV) после вычисления author ColorGrade exposure, но до final HDR composite / ACES / sRGB / LUT / Shader Graph и UI. Это означает, что фиксированный EV и художественная ColorGrade exposure композиционно перемножаются, но автоматической адаптации в manual-режиме нет.

Manual EV из нативных вызовов и C++ профиля проверяется на finite и ограничивается [-12,+12] перед HDR; NaN/Inf не пропускаются в shader. При переходе в/из ручного режима camera-local exposure history инвалидируется; при возврате к автоматике выполняется новый замер текущей сцены вместо смешивания со старой яркостью. Ручной режим может работать сразу при первом кадре — в отличие от freezeExposure, требующего валидную предшествующую 1×1 адаптацию. При ошибке пользовательского Shader Graph fallback к composite(0) сохраняет fixed EV, поскольку filt[2] применяется вне PF_GRADE и PF_AUTO_EXPOSURE. При невалидном final pipeline отчёт не объявляет manual EV выполненным.

Native API:

prisma.setViewManualExposure(stableViewId, true, 1.5f);
prisma.setViewManualExposure(stableViewId, false, 0.0f); // explicit disable
prisma.clearViewManualExposure(stableViewId); // restore profile inheritance

Выбор setViewManualExposure(id,false,...) явно переопределяет авторский manualExposure=true; clear возвращает управление профилю и инвалидацией AE history. Overrides принадлежат stable presentation viewId, а не разрешению/позиции камеры. retireView, retireUnregisteredViews и shutdown удаляют их вместе с остальным per-camera state, не освобождая общие GPU texture caches.

Мягкий прямоугольник для HDR Metering#

Stage 58 круговая область остаётся default; Stage 59 добавляет meterBox=true с параметрами meterHalfWidth и meterHalfHeight в нормализованных координатах viewport. Радиус и feather прежней области сохранены. В ExposureMeterU добавлен regionBox (пятый vec4); kExposureLog через regionBox.z > 0.5 выбирает signed-distance box вместо circle. Разность X приводится к масштабу высоты кадра множителем aspect; у мягкой границы есть smoothstep(0,feather,signedDistance). TUV(q) обеспечивает одинаковое направление Y в GL/Metal, а прежний meterOutsideWeight >= 0.02 сохраняет ненулевые вклады вне области. Глобальная редукция (weighted log sum и weight sum) не изменена.

Native ExposureMeterRegion дополняет существующие поля bool box=false; float halfWidth=0.25, halfHeight=0.25 в конце структуры, сохраняя старые aggregate initializers. Сеттеры клэмпят finite размеры к [0.01,0.5], а ROI не входит в authoritative ECS. Отчёт camera view дополнен autoExposureBoxMetered (только для фактически закодированной экспозиции). В режиме manualEV никакой meterRegion на кадре не выполняется.

Fallback при сбое GPU metering#

Если HDR luminance pyramid не закончилась полноценной 1×1 текстурой (valid=false или pw/ph != 1), Prisma теперь не выделяет и не пишет ExposureView.history для этого замера. Старый per-camera sample инвалидируется, final composite продолжает работать без sampled Auto Exposure; в будущих кадрах может быть сделана новая попытка. Частично закодированные mip passes не выдаются за успешное адаптированное освещение, отдельного GPU sync ожидания не добавлено.

ViewEffectReport.manualExposureEncoded и manualExposureEV сообщают только об истинно выбранном и закодированном fixed EV на последнем resolve. autoExposureTextureSlot остаётся -1 для manual. Существующая матрица эффектов отмечает manual как выполненный через base/fallback HDR composite, без ложной необходимости ExposureLog pipelines. autoExposureBoxMetered показывается вместе с autoExposureRegionMetered только после реального GPU meter pass и последующего успешного composite. В редакторе эти параметры доступны из общего каталога с пояснениями и статусом по viewId.

Это не полноценный произвольный metering texture mask, GPU histogram, local exposure, физическая имитация камеры, TSR или решение всех Shader Graph ошибок. Дополнительные рендер-ветви остаются экспериментальными до настоящих GPU-тестов.

Stage 60 — graceful Shader Graph / LUT fallback с сохранением обычных эффектов#

Ранее Prisma::resolve() при ошибке пользовательского postfx Shader Graph (GLSL/MSL компиляция, неподдерживаемый sampler layout или невалидные input texture) мог в конечном итоге перейти сразу на composite(0), теряя исправные фиксированные Bloom, ColorGrade, LUT, Vignette и другие эффекты. Теперь PRISMA использует следующую упорядоченную систему fallback:

  1. Запрошенный вариант со Shader Graph и, при наличии, GPU Auto Exposure.
  2. Тот же Shader Graph, но без Auto Exposure, если первая попытка не создала pipeline.
  3. Без Shader Graph: полный fixed-effect mask с Auto Exposure (если подготовленная HDR 1×1 текстура ещё доступна).
  4. Тот же fixed-effect mask без Auto Exposure, если предыдущая pipeline не поддерживается.
  5. Только как последняя возможность — composite(0) без фиксированных эффектов. Если даже он недоступен, диагностика не заявляет успешный draw.

Набор фиксированных эффектов сохраняется отдельной копией fixedMask до попыток Shader Graph. Если пользовательская текстура Shader Graph отсутствует или не была загружена в GPU, весь Shader Graph исключается из текущего composite, а исправные fixed effects продолжают работать. Успешное создание Shader Graph pipeline само по себе не означает, что input textures загрузились: graphInputsReady проверяет graphTextures_[path].valid() для всех используемых путей после попытки upload. Отсутствующий input больше не представляется молча валидной «чёрной» текстурой внутри выполненного Shader Graph.

Особенно важно после Stage 55: в graph-варианте с четырьмя изображениями Auto Exposure использует TEX9. Если graph не прошёл и используется fixed-only fallback, последняя реально выбранная pipeline требует TEX8. PrismaCompositeTextureLayout::plan(...) теперь вычисляется повторно на основании фактически выбранного Shader Graph, а не исходного авторского списка текстур. Точно этот же exposureSlot используется в GPU binding, ViewEffectReport и shader variation. При graphless fallback текстуры в slots 5..8 не привязываются без необходимости. Сохранены HDR manual EV Stage 59, ColorGrade и настройки Auto Exposure, если итоговый variant поддерживается. Кэш composite(mask,graphData) и отложенная GPU-retirement ownership неизменны.

Диагностика и кэширование ошибок#

ViewEffectReport.shaderGraphFallback указывает, что авторский Shader Graph был пропущен, а остальная цепочка смогла быть использована там, где валидны её pipelines. EffectExecution для ShaderGraph получает encoded=false и конкретную причину: отсутствие/upload текстуры либо shader compile/composite failure. У исправных fixed effects encoded определяется итоговым GPU mask, а не фактами исходного запроса. В редакторе PRISMA — Постобработка появилось соответствующее предупреждение по стабильному viewId.

У Prisma::lut() ошибка чтения, некорректная LUT strip N²×N и ошибка GPU upload теперь устанавливают lastError() с описанием и project-relative path. LUT по-прежнему negative-cached, поэтому остальные эффекты могут продолжать работать без него. graphTexture() теперь negative-caches также ошибки GPU upload: повторная декодировка и неудачное createTexture в каждом кадре не нужны. Сброс кэша через существующий setImageLoader() retire-ит успешные texture handles за реальным GPU fence и позволяет повторить загрузку; изменение файла на диске без вызова этой процедуры само по себе не является live-reload и не обещается в данном этапе.

Не изменились format postfx в game.json, PrismaData каталог, MCP API, ECS gameplay, настройки эффектов по умолчанию, SpectraFX, per-view exposure ownership или пользовательские Shader Graph форматы.

Stage 61 — reactive прозрачные края для Motion Blur и безопасный FXAA#

В Stage 61 исправлены два конкретных presentation-пути PRISMA: SDR FXAA больше не подменяет input невалидной текстурой при неудачном создании промежуточного render target, а optional Motion Blur умеет подавлять смешивание цветовых проб по разнице reactive coverage на краях полупрозрачных объектов/частиц. Работа остаётся независимой от жанра и не затрагивает authoritative ECS или отдельную SpectraFX.

Motion Blur + reactive input#

Новый необязательный параметр существующего motionBlur: reactiveTapRejection, диапазон 0..1, default 0. Он добавлен в конце каталога эффектов PrismaData.cpp, поэтому все предыдущие numeric offsets, старые postfx JSON, пресеты и native/volume profiles остаются совместимыми. При нуле действует прежний шейдерный вес и прежний фильтр.

MotionBlurU получил пятый vec4 tapInfo. Только kMotionBlur использует расширенную UBO; остальные pass-ы (Temporal, DoF, Bloom, FXAA, ExposureLog) и формат reactive texture не менялись. tapInfo.x получает reactiveTapRejection только при валидном входном MotionTextureInput (RGBA8, размер текущего scene render target, проверка declared metadata и доступного RHI textureInfo). Когда reactive mask отсутствует/отвергнута, значение нулевое, шейдер сохраняет прежнее поведение.

Если фильтр активен, текущий pixel и его соседние цветовые пробы читают TEX3 reactive R. Пробы с существенно другим coverage получают уменьшенный вес: keep *= 1 - strength * smoothstep(0.1,0.8,abs(tapReactive-centerReactive)). Это дополнение к уже существующей глубинной фильтрации (hardware или линейная depth), а не её замена. Если сумма весов нулевая, применяется исходный резкий RGB. При новых HDR прогонах Motion Blur возвращает исходную alpha centerColor.a, не 1.0, поскольку постэффект изменяет radiance RGB, не прозрачность сцены. Canonical TemporalResolve по-прежнему сам записывает глубину в собственную history alpha — этот контракт не изменён.

Зависимость от реальной reactive geometry: mask строится отдельно Renderer3D и дополнительными провайдерами (например, particles/water), а временное изображение mask НЕ сохраняется между кадрами. Данный этап не пытается исправлять отсутствующее покрытие у конкретного материала или считывать GPU пиксели на CPU.

ViewEffectReport по каждому stable viewId теперь хранит reactiveInputSupplied, reactiveInputAccepted и motionBlurReactiveEdgesEnabled. Это CPU metadata/RHI acceptance, а не GPU pixel validation: legacy borrowed handle без metadata может считаться допустимым, когда backend не предоставляет introspection. Последнее поле становится true только когда MotionBlur фактически закодирован, нужный вход проверен и strength больше нуля. Editor PRISMA показывает доступность mask и status фильтра.

Безопасная деградация FXAA#

Ранее SDR prepass делал src=target(kAa) до проверки, валиден ли результат создания. При failed RGBA8 target или depth attachment composite мог сэмплировать невалидный src. Теперь fxaaInput сохраняет оригинальную scene/post-chain текстуру, fxaaOutput создаётся отдельно, и prepass исполняется только если input/output и depth валидны. Graph FXAA (opt-in) и обычный direct draw используют те же два проверенных handles, а src=fxaaOutput назначается только после encoded draw. Если выделение не удалось, остальная цепочка продолжает с прежним src, без ложного fxaaEncoded=true.

Для HDR fallback FXAA, который применяется после финального Composite и только если TemporalResolve не сработал, добавлена проверка pipe.valid() до начала промежуточного AA target/pass. Это исключает чтение пустого composite target, если pipeline вообще не удалось получить. Проверка output target/depth сохранена. TAA и FXAA остаются взаимоисключающими на едином HDR presentation output.

Никаких новых GPU history или shared texture owners не введено. Рендер поддерживает текущие fence-retirement контракты Stage 54.

Stage 62 — reactive mask на первом кадре, Camera Cut и resize#

С этого этапа Renderer3D разделяет два независимых presentation-производителя: (a) объектные velocity vectors, требующие предыдущей камеры и истории текущих/прошлых transform-ов, и (b) current-frame RGBA8 reactive coverage, которой не нужна предшествующая поза. Ранее весь reactive pass находился внутри if (history.target.valid() && history.depth.valid()), а функция выходила с return на первом кадре, при camera cut и resize. Поэтому прозрачность воды, частиц, morph/skinned translucent объектов могла не покрываться reactive mask именно там, где temporal history недействительна.

Новая структура Renderer3D#

renderObjectMotionVectors(PostProcess&) продолжает вызываться на завершающем scene frame, до Prisma::resolve. В нём velocityHistoryReady определяется только по previousCameraValid && history.valid && !resize. При отсутствии предыдущих данных никакие ложные/нулевые object-motion velocity кадры не отправляются в Prisma. Текущие rigid/animated transform-позы собираются как прежде; после reactive-прохода они сохраняются для следующего кадра. Если viewport поменял размер, target/depth/reactive текстуры все помещаются в существующую GPU-fenced очередь через queueObjectMotionTexture(...), а не уничтожаются синхронно. Это сохраняет Stage 54 ownership contract.

Новый приватный метод Renderer3D::renderCurrentFrameReactiveMask(PostProcess&, ObjectMotionHistory&, gfx::TextureHandle sceneDepth,int w,int h) использует только текущий viewProj_, model poses, scene depth и готовые framebuffer размеры. Этот helper вызывается после условного object velocity прохода и не вложен в него. Он сам обеспечивает private depth attachment для reactive-only кадров (Depth) и при наличии нужной геометрии создаёт RGBA8 reactive target. Scene depth от Prisma передаётся как borrowed sampler и никогда не становится writable depth attachment. Отсутствие RGBA16F velocity не блокирует helper на уровне Renderer3D, если native post hook запросил такую reactive работу и предоставил scene depth; обычная Prisma HDR-политика по-прежнему сама решает, нужен ли ей MotionBlur/Temporal Resolve вообще.

Рендер current coverage сохраняет прежние источники: rigid прозрачные модели и fading LOD, morph/skinned/baked translucent модели с current pose для обеих motion матриц, immediate water MeshVertex-геометрию, motionReactiveDraws_ от частиц и custom native providers. Маска по-прежнему создаётся/clear-ится только на текущем кадре, blending объединяет coverage, передаётся в Prisma как MotionTextureInput::declared(reactive,w,h,RGBA8). Варианты, где нет reactive geometry/callback или нет доступного depth/target/pipeline, не объявляются успешным reactive pass.

Раздельная статистика и диагностика#

Renderer3D::ObjectMotionStats теперь имеет: velocitySeedOnly — первый кадр / invalid/cut/resize, чтобы не выдавать pose initialization за GPU object velocity; и reactiveSubmitted — отдельный флаг фактически закодированного current-frame mask. Историческое submitted остаётся показателем object-velocity прохода, не reactive-only.

Камера PRISMA хранит ViewEffectReport.objectVelocityInputAccepted и reactiveWithoutObjectVelocity с учётом отдельной MotionTextureInput проверки: сначала проверяются declared width/height/format, затем RHI textureInfo, если backend поддерживает introspection. Эти поля не доказывают содержимое пикселей GPU. Editor показывает mask-only pass для reactive coverage без валидной object velocity texture; отдельный статус MotionBlur reactive edge rejection продолжает зависеть от реально encoded blur и настроенного параметра.

Сохраняются без изменений: стабильная идентичность per-view независимо от одинакового разрешения двух камер; resetObjectMotionHistory(viewId) и camera-cut epoch; GPU-fenced retirement; отсутствие ECS mutation; Prisma::resolve и HDR temporal history как единственного color history owner; HUD вне постобработки. Reactive mask не становится долгоживущим temporal input.

Stage 63 — точная rigid alpha-cutout / dissolve reactive coverage и lifecycle callbacks#

Этот этап расширяет текущий Renderer3D::renderCurrentFrameReactiveMask (Stage 62), не меняя архитектуру, формат Prisma/MCP, HDR color history или ownership Reactives. Reactive mask остаётся RGBA8 current-frame входом от Renderer3D в PRISMA; пер-камерная история движения является независимым компонентом.

Rigid-модели: точный AlphaMask, dissolve и LOD#

Для rigid-моделей с AlphaMode::Mask или dissolve > 0 добавлен отдельный шейдерный вариант reactive_shaders::kCutoutVS/kCutoutFS/kCutoutMSL и objectMotionReactiveCutoutPipeline_. Основной water/transparent/mesh pipeline оставлен без изменений.

Шейдер повторяет фрагментные условия обычного ModelShaders: baseTex alpha, baseColor.a, опциональную vertex alpha (с исключением vertex-occlusion/AO), alphaCutoff, KHR base-UV offset/scale/rotation, screen-space 4×4 LOD dither и тот же object-space noise modelNoise3(opos*7)*0.7 + modelNoise3(opos*19)*0.3 для dissolve. TeamMode::BaseAlpha использует baseColor alpha без baseTexture alpha; для TeamMode::VertexAlpha не умножает alpha vertex дважды, следуя материалу. Сцена по-прежнему сэмплирует чужой sceneDepth только на чтение; реактивный pass имеет собственный writable history.depth. Используется BlendMode::Screen для объединения coverage. Shader source предоставляет одинаковую логику отсечения GLSL и Metal, но GPU parity требует настоящих shader tests.

Новый uniforms layout только для этого pipeline: ReactiveCutoutUniforms {mvp,params,lod,uv0,uv1,maskInfo}, 144 bytes. Vertex attributes — настоящие ModelVertex position[0], uv[2], color[4]. AlphaCutout texture bind slot 1, scene depth в slot 0. Поскольку шейдер точно отбрасывает alpha holes, реактивность больше не закрашивает целый треугольник у foliage/grilles. Shader Graph vertex displacement и geometry-driven models по-прежнему требуют отдельных производителей coverage; не заявлять их как поддержанные данным rigid-путём.

Анимированные переходы и callbacks#

Для skinned/morph/baked translucent моделей kAnimatedFS и его MSL-генератор получили необязательный U1.reactiveLod (fragment buffer(2)) с точным 4×4 LOD dithering на текущем кадре. Анимированные LOD и dissolve теперь подают coverage и при отсутствии previous pose. Dissolve у анимированных объектов консервативный — маска может покрывать фрагменты, которые основной ModelShaders отбрасывает по object-space noise. Точный анимированный alpha-cutout/actor aperture требует нового current-object-space varying или отдельного material-specific shader, не реализован здесь.

В Renderer3D readiness маски проверяется по необходимому источнику: отдельно simple rigid, cutout/dissolve rigid, skinned, baked, MeshVertex или motionReactiveDraws_. Наличие неподходящего заранее созданного shader (например, skin pipeline при отсутствии baked pipeline) больше не является основанием публиковать пустую reactive mask. Когда callback был зарегистрирован на текущий scene frame, но активный postprocess, scene depth или mask pipeline недоступны, ObjectMotionStats.reactiveCallbacksDropped учитывает невыполненные вызовы; callback не переносится на следующий кадр.

Registration contract прежний: addMotionReactiveDraw после beginScene, но до resolvePrisma. Рендерер вызывает callbacks только с открытым масочным pass: поставщик должен лишь записывать draws, не вызывать beginPass/endPass, сохранять свои GPU ресурсы до завершения submission и комбинировать coverage без уничтожения предыдущих пикселей. Список очищается после resolve, при неактивном postprocess или в начале нового scene frame. Промежуточная маска не кэшируется между camera cuts и не переносится между viewId.

Renderer3D::ObjectMotionStats дополнен cutoutReactiveDraws, dissolveReactiveDraws, reactiveCallbacksDropped; прежние reactiveDraws/reactiveAnimatedDraws/ reactiveCallbacks/reactiveSubmitted сохранены. Счётчики означают CPU-encoded submissions / callback invocations, а не GPU completion или доказанное содержимое пикселей. Общий per-view Prisma::ViewEffectReport из Stage 62 и GPU-fenced retirement Stage 54 не изменялись.

Stage 64 — precise animated reactive alpha/dissolve и Actor Reveal#

Stage 64 завершает bounded functionality пробела, найденного в Stage 63: animated skin/morph/baked reactive coverage раньше создавалась только как консервативный силуэт, без применения материального AlphaMode::Mask, object-space dissolve и локального kDrawActorReveal aperture. В новой реализации обычная velocity pipeline остаётся без изменений, а reactive path получает отдельный GPU shader variant.

Reactive-only vertex stage#

Renderer3DReactiveShaders.h теперь предоставляет две проверяемые функции генерации: reactive_shaders::animatedVertexGlsl(source,baked) и reactive_shaders::animatedMsl(source,baked). Они принимают существующие kDeformedVS/kDeformedMSL или kBakedVS/kBakedMSL, подставляют UV (ModelVertex атрибут 2), vertex color/alpha (атрибут 4) и current deformed object-space pose, сохраняя прежние skin/morph/baked источники (атрибуты 5/6, U0/U3/U4/U5 и texture 7/8). Результирующие локальные текстовые варианты передаются в createShader; оригинальные motion shaders и velocity output остаются прежними. Если ожидаемый source anchor отсутствует, генератор возвращает пустую строку, а Renderer3D не создаёт невалидную реактивную pipeline.

kAnimatedFS (GLSL) и создаваемый MSL fragment используют новый ReactiveAnimatedU1, 160 bytes: lod[4],uv0[4],uv1[4],maskInfo[4],world[16], reveal[4],revealAxis[4]. Он занимает обычный uniform slot 1 (Metal buffer 2), не мешает skin/baked deformation слоту U3/U4/U5. Шейдер по-прежнему рендерит только current-frame RGBA8 reactive coverage, не записывает скорость и не использует предыдущую кадровую историю. Depth сэмплируется из чужого sceneDepth, а writable attachment — renderer-private history.depth.

Для animated объектов теперь точно воспроизводятся те же условия отсечения текущего кадра: 4×4 LOD dither, UV offset/scale/rotation, материальный cutoff baseTex alpha * baseColor alpha (+ vertex alpha, если допустимо), и modelNoise3(currentDeformedLocalPos * 7) * 0.7 + modelNoise3(currentDeformedLocalPos * 19) * 0.3 для dissolve. Настройки TeamMode::BaseAlpha и TeamMode::VertexAlpha не перемножают вершинную/текстурную alpha дважды; vertex occlusion/AO не трактуется как opacity.

Actor Reveal для rigid и animated#

kDrawActorReveal с активным Renderer3D::actorReveal теперь делает модель источником reactive coverage, даже если она полностью opaque и не имеет LOD fade/dissolve. Только главный camera pass (geometryMainView_) передаёт world-space actor center/radius, camera axis и view-dependent attenuation из той же Renderer3DModels.cpp формулы. Fragment shader повторяет aperture: radial=length(delta-axis*depth), radius=actorRadius*max(0.01,1-depth*axisScale), coverage=(1-smoothstep(radius*.48,radius,radial))* smoothstep(.04,.24,depth) и 4×4 dither discard. В неактивном режиме reveal.w=0 и этот путь не влияет на маску.

Для rigid alpha/dissolve shader был расширен ReactiveCutoutUniforms с 144 до 240 bytes, за счёт world matrix и reveal/axis в U0. GLSL и Metal получают current world position вершины. Для animated используется current deformed local position, преобразуемая через переданную world матрицу во fragment. Это не отдельный draw pass и не ECS-система: источником остаётся тот же current-frame reactive pass из Stage 62.

В Renderer3D::renderCurrentFrameReactiveMask replay анимированных материалов теперь настраивает ReactiveAnimatedU1, отдельный baseTexture sampler slot 1 и вершинные атрибуты UV/color/skin. Параметры actor reveal, dissolve, alpha cutoff и LOD задаются по каждой ModelItem. Статистика ObjectMotionStats.actorRevealReactiveDraws дополняет существующие cutoutReactiveDraws, dissolveReactiveDraws, lodReactiveDraws. Это CPU-encoded draw counts, не подтверждение GPU-видимости. Ресурсы остаются за Renderer3D; existing GPU-fenced target retirement и stable per-viewId ownership не изменены.

Ограничения и проверка#

Поддерживается точная исходниковая формула обычных alpha/dissolve/reveal для rigid и animated моделей. Не заявляется per-pixel паритет с произвольными material Shader Graph, vertex displacement, кастомными transparent pipeline, GLES/Metal depth conventions или правильная многослойная прозрачность — их должны обеспечить отдельные реактивные providers или native GPU validation. GPU shader permutations ещё не скомпилированы и не выполнены на устройстве.

Новое исправление: native и JSON numeric safety#

parsePrismaEffect теперь не принимает нечисловые RGB компоненты и не пропускает NaN/Inf через std::clamp. Значения Number/Color проверяются как finite double, ограничиваются по каталожному диапазону до приведения к float. При strict MCP validation ошибка становится std::runtime_error; в обычном режиме проблема добавляется в issues, а некорректный параметр (или полный RGB-triplet) остаётся исходным default. Корректные старые профили сохраняют поведение.

Новый sanitizePrismaSettings(PrismaSettings&) в PrismaData.h/cpp — GPU-free нормализатор прямых native/ECS профилей: восстанавливает missing flattened values из default-каталога, отбрасывает лишние, заменяет non-finite на default, выполняет range clamps и нормализует boolean 0/1. Он вызывается в Prisma::setSettings до сохранения базовых настроек, а PrismaVolumeStack::resolve выполняет его на конечном смешанном camera profile. В обычных исходниках рендера эти гарантии не добавляют GPU пасс, шейдер или новые ресурсы.

Opt-in physical atmosphere and local volumetric fog (2026-11-20)#

PRISMA owns PhysicalSky and LocalFog HDR passes. They run before exposure metering and motion/temporal processing, then normal bloom/tonemap. New target roles 200/201 do not overlap DoF (50), metering or motion buffers. Sample scene depth with the existing separate scratch depth attachment; size resources use PRISMA's normal fence-retirement path. Pipelines shut down after its GPU-idle barrier. No second PostFx implementation or SpectraFX emitter ownership.

See physical sky/clouds/god rays and local sphere/OBB fog with runtime reveal. The read-only PHYSIS bridge targets Prisma&; the legacy PostFx alias remains compatible. These features are disabled by default. Native region/settings APIs are owner-wide: a multi-camera host must set each view's cosmetic data before its resolve, or use a separate Prisma owner. Camera-volume profile blending does not yet author or interpolate these atmosphere settings. No gameplay changes.

Structured fog continuation#

FogVolume::structure optionally shapes local fog with periodic 3D noise, per-axis world scale, height attenuation and wind; Prisma::setLocalFogTime provides a reproducible presentation clock. Default uniform fog is preserved. The existing local fog pass owns this, with no extra history or render targets. See the structured banks section in docs/local-volumetric-fog.md. No terrain sampling, gameplay visibility or PHYSIS state mutation is introduced.

Local fog now also supports heightVariation, three-dimensional warp, boundary edgeErosion and optional selfShadow/shadowDistance. Self-shadowing ray-marches all active volumes and reveal holes toward the sun, independently of the existing geometry shadow map. This is bounded single scattering; no new temporal buffers, shadow-map ownership, terrain dependency or authoritative simulation state.

Inspector graph-v2 preview composition (2026-11-20)#

The integrated optional spectra::GpuPoolWorld editor preview contributes through Editor::drawSpectraGpuPreview() in the same open HDR scene pass, immediately before Renderer3D::resolvePrisma(). SpectraFX owns emitters, per-frame simulation and particle GPU resources. PRISMA retains the full-screen resolve, camera volumes, reactive coverage and viewport GPU timing. Main's existing completion timeline is preserved; no new postprocess implementation or renderer default is introduced. See docs/agent-handoffs/inspector-spectrafx-main-2026-11-20.md for integration verification and remaining UI/platform coverage.

Optional water on the lens#

The independent lensWater catalog effect is opt-in, configurable and removable without disabling NEREID underwater absorption. See parameters and host contract. NEREID supplies read-only camera immersion; PRISMA owns bounded per-view wetness, post-exit drainage/drying and the shared GLSL/MSL composite. This is a screen-space approximation; see the separate stage handoff for actual GPU/test coverage.

Per-view physical-lens defocus (LENS P2, stage 96)#

Prisma::setViewDepthOfField(viewId, DepthOfFieldOverride{enabled, focusDistance, focusRangeMeters, maxBlur}) replaces the metric focus plane, sharp interval and maximum blur of the authored depthOfField effect for one stable view, in the same way setViewManualExposure overrides the authored exposure. The override forces the metric (camera-linear) branch and keeps the effect's intensity and occlusionToleranceMeters. enabled=false switches defocus off for that view. Values are clamped to the catalog bounds on ingress; clearViewDepthOfField and retireView remove the override. It still requires the authored effect and AIVERSE_PRISMA_DOF=1; nothing is added to the profile implicitly.

LENS drives it from CameraLensComponent::driveDepthOfField through CameraPostFxPool: the thin-lens sharp interval [near, far] becomes focusDistance = (near+far)/2, focusRangeMeters = far-near (an infinite far limit is capped at 500 m) and maxBlur = background disc radius at infinity in render pixels (clamped to 16). This is the same 8-tap screen-space defocus, not a physical bokeh. See docs/handoffs/prisma-stage-96-lens-physical-dof.md.
